Lesson 0102 · The Engineer's Prompt

Think in Systems, Not Steps

A junior ships a component that works; a senior ships a component that survives its neighbours. This lesson turns "fix this" into a prompt that makes the AI see data flow and failure modes before it writes code.

By the end you can draw your app's data flow and name three ways it breaks, and ask the AI for that diagram first — evidenced by a one-page map of frontend → backend → FalkorDB → LLM → back with three failure modes.

Stop asking "does this work?" and start asking "what happens when this slows down, times out, or disappears?" Systems thinking is a skill, not a talent: you build it by drawing boundaries and rehearsing failures before the code exists.

The idea

Systems thinking is "the cognitive framework that allows engineers to see software not as isolated components, but as interconnected, dynamic systems with emergent properties, feedback loops, and non-obvious failure modes." The same source names the four things you look for: boundaries and interfaces (where your control ends and assumptions break), feedback loops (outputs that feed back into inputs — retries, caching, auto-scaling), emergence (system-level behaviour that no single component shows), and resilience (keeping function under disturbance) [1].

The key move is small: for any change, ask where does data come from, where does it go, and what fails if this breaks? Then run failure-mode analysis — "what happens when the DB is slow? when the LLM times out? when a tenant is missing?" — before you write a line. Senior engineers "do this almost unconsciously during design reviews, rapidly cycling through failure scenarios" [1]. You can install the same reflex by making the AI do the cycling for you.

Your app is exactly such a system. A single prompt today fans out across four asynchronous hops, and each hop is a boundary you don't control:

frontend (cockpit)
   │ POST /prompt  (tenant key)
   ▼
backend (Node/TS)  ──►  LLM (Gemini)        ← network + timeouts
   │                        │
   │                        ▼
   └──►  FalkorDB  ──►  write fans out to 4 agents
             (MERGE)         │
                             ▼
                     handoff ledger (:HANDED_TO)
                             │
   ◄──◄─ response ◄───── 4th agent may straggle ◄──◄─┘

Now run failure-mode analysis on the fan-out. A write that fans out to four agents is a feedback loop: each straggler that retries adds load, which slows the graph, which triggers more retries — the classic retry storm where "the retry mechanism — designed to improve reliability — actually prevents recovery" [1]. Three concrete failure modes hiding in that diagram:

BoundaryWhat breaksBlast radius
LLM callTimes out mid-fan-out; three agents wrote memory, the fourth never did; handoff ledger is now half-completeSilent, permanently inconsistent graph
FalkorDB (MERGE fan-out)Graph slows under 4 concurrent writers; one tenant's heavy prompt starves the othersCross-tenant latency, not just one user
Tenant keyMissing tenant → write lands in the wrong graph or nowhereMemory leak between tenants

None of these are visible by reading a single function. They emerge from how the parts interact [1]. That is precisely why the prompt below asks for the map first.

Do it

Compare the two prompts. The weak one hands the AI a symptom and gets a patch for the symptom. The senior one hands it the system and asks for prediction before code.

"The 4-agent run sometimes hangs. Fix it."

→ gets a timeout bumped or a spinner, and the underlying fan-out still corrupts the ledger. The AI never saw the system because you never showed it.

"Here's my data flow: frontend → backend POST → Gemini → FalkorDB MERGE fan-out to 4 agents → handoff ledger. A write fans out to 4 agents. Before any code, draw this flow as a diagram and predict where it breaks when (a) the LLM times out mid-fan-out, (b) the DB is slow under concurrent writers, (c) the tenant key is missing. For each, name the blast radius and the smallest change that contains it. Then wait for my go-ahead."

Same bug. The senior prompt gets you the diagram, the failure modes, and a containing change — and it keeps you in the loop before the AI commits to a fix you don't understand.

A teammate says "the write to FalkorDB works, all 4 agents get their nodes." Which question is the senior one?

Sketch your app's data flow and list three failure modes.
  1. Open a blank page (or notes/dataflow.md). Draw frontend → backend → FalkorDB → LLM → back as boxes and arrows. Label each arrow with: the data it carries, the protocol, and who owns each side of the boundary.
  2. Mark the fan-out: where one request becomes writes to multiple agents. Circle every place the flow retries or blocks the caller.
  3. Under the diagram, list 3 failure modes — one per boundary (LLM, FalkorDB, tenant key). For each: what breaks, and what the user or the ledger sees afterwards.
  4. Paste the senior prompt above into the AI, replace the fan-out sentence with your real diagram, and check its prediction against your three.
