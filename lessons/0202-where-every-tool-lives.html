Lesson 0202 · Toolchain & Setup

Where Every Tool Lives

You have eight moving pieces and no map. This lesson pins each tool to a spot in the data flow and gives you the one test that proves it matters: remove it and name what breaks.

By the end you can place every tool on your diagram and say what dies if it is removed, evidenced by a one-page map of frontend → backend → {FalkorDB, LLM, tools, tracing} with a break-test note on each box.

A tool you cannot place on a diagram is a tool you cannot debug. Before you wire anything, draw the flow and label every box with its protocol and its owner. Systems thinking starts with boundaries, and a boundary you can point to is a boundary you can test.

The idea

Your app is one system with a single spine: the cockpit asks, the backend reasons, the graph remembers. Every other tool hangs off that spine. Draw it once and the whole submission becomes navigable:

React + Vite cockpit  (browser)
   │  HTTP / SSE         ← the only thing the user sees
   ▼
Node/TS backend  ───────────────────────────────┐
   │  orchestrator: planner → researcher →       │
   │               actor → critic  (hand-rolled)  │
   ├──► FalkorDB   (falkordb npm client, Cypher)  │  memory graph
   ├──► Gemini     (extraction + reasoning)       │  LLM
   ├──► Tavily     (web-search tool the agent calls)
   └──► LangSmith  (traces every LLM + tool call) ┘
            ▲
            │  MCP = the standard plug that exposes
            └─ FalkorDB + Tavily as agent-callable tools

FalkorDB is the load-bearing memory graph — the whole Track 02 story. Per D5 it holds the three-tier memory model (episodic, semantic, procedural) in one connected graph, and per D2 the hand-rolled orchestrator persists its state in it. Multi-graph / multi-tenant topology gives each tenant a separate named graph in one instance. The backend talks to it with the official falkordb npm client and writes with idempotent MERGE.

The backend hosts the hand-rolled orchestrator (D2): a small explicit state machine, not a framework, whose checkpointer is FalkorDB. It calls Gemini for extraction and reasoning, and calls Tavily as a web-search tool. MCP (Model Context Protocol) is the standard way to expose FalkorDB and Tavily to an agent — "an open-source standard for connecting AI applications to external systems," a USB-C port for tools [3]. LangSmith traces every hop.

The break test

For each tool ask: if I delete this box, what stops working? If the answer is "nothing," the tool is not load-bearing and the judges will notice.

The rule-3 line. FalkorDB must be the box that, when removed, breaks the memory system — not one that merely slows it. If the cockpit still works without FalkorDB, you have a simulation, not a submission.

MCP, concretely

MCP servers are the plugs. FalkorDB's server runs via npx and reads its connection from the environment [1]:

FALKORDB_HOST=localhost FALKORDB_PORT=6379 npx -y @falkordb/mcpserver@latest

Tavily's server exposes tavily-search and tavily-extract over the same protocol [2]:

TAVILY_API_KEY=... npx -y tavily-mcp@latest

You wire both to opencode so you can query the graph and search the web from the agent — the same tools your backend will call. LangSmith is set up by creating an API key and adding tracing via environment variables or the SDK [4].

What else you need

The diagram is the skeleton; these are the parts that make it runnable and submittable:

  • Secrets via .env — Gemini key, TAVILY_API_KEY, LANGCHAIN_API_KEY, FalkorDB host/port. Never commit them; commit .env.example.
  • Docker Compose — one docker compose up starts FalkorDB + backend + frontend (D4). Local-first removes a whole class of network failures.
  • A health check — npm run health prints MATCH (n) RETURN count(n), so "is the graph alive?" is one command.
  • queries.cypher — the real Cypher you run, in the repo, so the graph data model is provable.
  • A demo video — shows the flip: stop FalkorDB, watch the memory break.
Draw the map yourself — it is the artifact this lesson produces.
  1. Open a blank page (or notes/tool-map.md). Draw frontend → backend → {FalkorDB, LLM, tools, tracing} as boxes and arrows, following the diagram above.
  2. Label each arrow with its protocol (HTTP/SSE, Cypher, HTTPS, MCP stdio/http) and who owns each side.
  3. Beside every box write its break test: remove it → what breaks. Mark the one box that breaks the system, not a feature — that must be FalkorDB.
  4. Check it against reference/tool-integration.html and fix any box you placed in the wrong layer.
