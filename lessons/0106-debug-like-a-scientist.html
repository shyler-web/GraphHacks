Debug Like a Scientist

You do not find a bug by changing lines until it disappears. You find it by reproducing it, forcing three ranked hypotheses, and letting the cheapest test tell you where it lives.

By the end you can turn a vague failure into a confirmed repro plus three ranked hypotheses before touching any code, evidenced by a repro that fires on demand and a hypothesis table naming the one cheapest discriminating test.

Why this matters

Your Track 02 build has a simulated backend to replace with real FalkorDB, and the failures ahead are predictable: Docker not up and port 6379 refused, the client failing to connect, a Cypher syntax error, a React fetch returning a blob instead of JSON. Each has a different root cause and a different fix. If you prompt "it doesn't work, fix it," a model will happily patch a plausible cause that has nothing to do with the actual failure — and you will have lost the afternoon with nine files touched and no idea which change mattered.

The prompt is downstream of the diagnosis. You cannot direct an agent to fix what you have not reproduced.

No confirmed repro, no fix. Write expected, observed, and the reproductions steps before any theory, and force at least three hypotheses before chasing one.

The idea

Debugging is the scientific method in miniature: observe, hypothesise, predict, test, update ([SiliconWit](https://siliconwit.com/education/critical-thinking-engineers/debugging-as-reasoning/)). The practical loop runs in a fixed order ([MaxtDesign](https://maxtdesign.com/learn/developer-tools/systematic-debugging-method)):

  1. Reproduce reliably. Nail expected, observed (the exact error text, not "it crashes"), and the minimal sequence. "If you cannot trigger it on demand, that is your whole problem right now, and the work is to find a reliable repro, not a fix."
  2. Force three hypotheses. Even when one feels obvious. The claim is the suspected cause; the test is the cheapest experiment that would prove it false; the prediction says what you will see if true versus false. Writing the prediction first is what keeps you honest.
  3. Rank by likelihood × ease of test. Not likelihood alone: "a hypothesis that is probably right but takes four hours to test is a worse next move than one that is possibly right and takes thirty seconds." Cheap tests collapse the search space fastest.
  4. Run the cheapest discriminating test. Confirmed → you have the root cause. Falsified → do not start over; log it, re-rank, repeat.
  5. Fix the root cause, not the symptom. Minimum change to the confirmed cause; resist refactoring the neighbourhood.
  6. Add the regression test that would have failed before the fix and passes after, in the same commit.

The failure mode this prevents is the one worth naming: "the single most common way AI-assisted debugging goes wrong is the model proposing a confident fix for a bug nobody reproduced" ([MaxtDesign](https://maxtdesign.com/learn/developer-tools/systematic-debugging-method)).

You have not reproduced the FalkorDB connection failure yet. What is the correct next instruction to the agent?

Reproduce one real error in your repo and tabulate three hypotheses before changing any code.

  1. Pick one genuine failure — most likely nc -z localhost 6379 refused, a client connect error, or a bad Cypher query. Get it to fire on demand.
  2. Write the three lines: Expected, Observed (paste the exact error), Repro (numbered steps). If it will not fire on demand, stop — writing the repro is the task.
  3. Write the hypothesis table: three rows of cause · cheapest test · prediction. Rank by likelihood × ease of test and circle the top row. Do not run it yet.
  4. Run only that one test. Log the result. If falsified, re-rank; if confirmed, fix the root cause and write the regression test in the same commit.
