Extend to Tracks 1 & 3

Your Track 02 memory graph already holds connected, remembered, explainable data. Tracks 01 and 03 are not rewrites — they are the same foundation with a different schema, a different tool set, and a different demo story.

By the end you can write a concrete, low-cost extension plan for Track 01 or Track 03 — evidenced by a one-page plan naming what changes, what stays, and three schema changes.

The graph database, the backend, the tracing, and the orchestrator are the expensive, slow-to-change parts. The schema and the tool set are where the tracks actually differ — so decide track fit by asking "what nodes and edges does this story need?", never "do I rebuild?".

The idea

The hackathon runs three tracks, and you may enter one, two, or all three — each has its own prize [1]. They are described as different points on the same idea: an agent that acts on data fits Track 01, one that remembers or coordinates fits Track 02, and one that works with company knowledge fits Track 03 [1].

Track 01 — add algorithms, let the agent act

Track 01 wants an agent that decides and acts. FalkorDB exposes graph algorithms as first-class calls — CALL algo.<name>() with a YIELD clause — using matrix-based computation for speed [2]. The ones the brief names map directly to agent questions:

QuestionAlgorithm toolActs on your semantic memory
"What breaks if this service goes down?"Shortest path (SPpath / Cypher shortestPath())Traces :Entity–:RELATES_TO fan-out
"Which node matters most?"PageRank / centralityRanks :Entity influence
"Which groups are isolated?"Weakly connected components (WCC)Splits disconnected subgraphs

The move is small: each algorithm becomes a :Tool node in your procedural memory, selectable through MCP, so the agent calls the algorithm instead of writing it [2]. The agent then acts on the result with a tool call, and you return the traversed subgraph as the explanation — which is Track 01's "explainable results" and your existing explainability feature, reused.

Track 03 — same graph, company labels

A Company Brain is the same semantic memory discipline with different entity types. You already have :Entity, :Fact, :Topic, and provenance via :DERIVED_FROM; Track 03 asks you to point those at people, teams, projects, documents, and decisions, then answer "who owns what, who knows what" and trace decisions back to their source [1]. The provenance edge you built for explainability is "tracing decisions back to their source".

Read that as the vertical slice argument: only the top of the stack is story-specific, so an extension is a bounded change, not a horizontal slab. This is a reversible decision if your schema stays additive.

You add Track 03 to your Track 02 submission. Which of these changes?

Write a one-page extension plan for a track you are not targeting (Track 03 recommended).
  1. List 3 schema changes for a Company Brain — for each name a new node label or edge type and the property it carries. Example: :Person {name, role}, :Decision {made_at, rationale}, (:Decision)-[:BASED_ON]->(:Document).
  2. Name 2 tools the agent needs and whether each is a graph algorithm (Track 01) or a schema query (Track 03).
  3. Write 1 sentence of the demo story, then 1 sentence on what still breaks if FalkorDB stops.
  4. Hand the page to the AI as a spec card and ask it to flag anything that secretly requires a rewrite.
