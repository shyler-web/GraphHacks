Running TypeScript in Node

Your memory service is TypeScript (decision D1), but the host runs Node v18.19.1 — and Node does not execute TypeScript. This lesson gives you the three ways to bridge that gap and the table to choose one, so the T2.2 verify command is a decision, not a surprise.

By the end you can choose how to run the TypeScript memory service on Node 18, evidenced by naming your option and its exact run command in one line.

Node runs JavaScript, not TypeScript. Every .ts file must be transformed to .js before Node executes it — either by a tool that strips types on the fly, or by a compiler that emits .js first. Pick the transform; the runtime is then trivial.

The idea

Node executes JavaScript. A .ts file is not JavaScript — it carries type annotations that Node's parser rejects. So something must transform it first, and there are two kinds of transform:

  • Type stripping — delete the type annotations and keep the code. Fast, and it does not check types. Node's built-in support "will replace inline type annotations with whitespace, and no type checking is performed." [1]
  • Full compile — translate TypeScript to JavaScript, including features that need real code generation (enums, namespaces), and report type errors. This is what tsc does. [3]

Node's built-in type stripping is new. It was added in v22.6.0, enabled by default in v22.18.0 / v23.6.0, and marked stable in v24.12.0 / v25.2.0 [1]. Node 18 predates all of it, so on this host there is no built-in path: you need a tool or a non-.ts runtime.

The engines warning is not a wall. The falkordb client declares engines.node >= 22, so npm prints EBADENGINE on Node 18 — but it installs and runs anyway. It was smoke-tested here (RETURN 1, MERGE write/read) [4]. Treat it as a signal that the client targets newer Node, not a hard failure.

The three options

OptionWhat it isExact command
A · tsxA TypeScript runner for Node; strips types on the fly, no build step [2]npm i -D tsx then npx tsx service.ts
B · .mjs + JSDocPlain JavaScript with types written in comments; no dependency, no .tsnode service.mjs
C · tsc → .jsCompile .ts to .js, then run the output; type-checks first [3]npx tsc then node dist/service.js

Decision table

Recommendation posture — you decide. Ask which cost you can pay. A gives the fastest dev loop and keeps real .ts, at the price of one dev dependency and no type checking at run time. C keeps real .ts and enforces types with no new dependency, at the price of a compile step. B adds nothing and needs no build, but abandons .ts — which sits awkwardly against D1. For a solo beginner under deadline pressure, A and C both honour D1; the tie-breaker is whether you value the missing build step (A) or the enforced types and zero new dependency (C).

What does the engines.node >= 22 warning from falkordb actually mean?

Do it

  1. Confirm the host: node --version → expect v18.19.1.
  2. Prove Node 18 cannot run TypeScript. Create a scratch file and run it: 
    printf 'const n: number = 1;\nconsole.log(n);\n' > /tmp/ts-run/hello.ts
node /tmp/ts-run/hello.ts
    Expected: SyntaxError: Missing initializer in const declaration, exit 1.
  3. Option A — run the same file with tsx (no install into the repo): npx --yes tsx /tmp/ts-run/hello.ts → expect 1.
  4. Option C — compile then run, using the typescript already in this repo: npx tsc /tmp/ts-run/hello.ts --target esnext --skipLibCheck --outDir /tmp/ts-run/out && node /tmp/ts-run/out/hello.js → expect 1.
  5. Write the one-line decision: "We run the memory service with ___ because ___." That command becomes the T2.2 verify command — 2 messages → 2 Turn nodes recalled in order [5].

Why this is the whole backend

This choice decides how every later task runs: the episodic write/recall in T2.2, the handoff ledger in T3.1, and the Vite route in T4.1 all execute through it. The good news is that the choice is reversible: the memory-service contract is language-agnostic [5], so swapping A for C later is a change to the run command, not the queries. Pick fast, verify with npm run health, and move on.
