Semantic Memory: Facts and Entities

Build durable factual knowledge as a graph: extract entities and relationships from a message, MERGE them, then query facts about an entity.

By the end you can turn one message into Entity nodes and typed fact edges, evidenced by a Cypher query that returns a true fact you never stored as text.

← Curriculum Prev Next → Cypher cheat sheet

Why this matters

Track 02 asks for semantic memory: "Factual knowledge about the domain, the knowledge graph itself. Entities, attributes, and relationships extracted from documents and databases" (FalkorDB). Your cockpit tracks conversation turns (episodic memory), but a demo that also knows "Alice works at Acme" — and can traverse from Alice to Acme — is the difference judges can see. This is the graph doing real work.

The idea

Semantic memory is not a notes table. It is a set of Nodes (entities) connected by Edge (relationship)s that carry meaning. The FalkorDB guide describes the ingestion step plainly: "During ingestion, an LLM extracts entities and relationships from source documents. Each entity becomes a node; each relationship becomes a typed edge."

You write facts with MERGE, "the clause that matches a pattern or creates it if it does not exist" — because MERGE "prevent[s] node duplication while allowing incremental memory updates." Write the same fact twice and you still get one node, one edge.

Semantic memory connects to episodic memory by sharing the same entity nodes: an episodic turn points at the entities it mentioned, so "what happened last time" and "what is true about Alice" live in one graph. The GraphRAG SDK traces this with provenance edges — it keeps MENTIONED_IN edges linking entity mentions to their source chunks (GraphRAG-SDK).

// Message: "Alice Johnson is a software engineer at Acme Corp in London."

// 1. MERGE the entities (idempotent — safe to re-run)
MERGE (a:Entity {name: "Alice Johnson"})
MERGE (org:Entity {name: "Acme Corp"})
MERGE (loc:Entity {name: "London"})

// 2. MERGE the typed fact edges
MERGE (a)-[:WORKS_AT]->(org)
MERGE (org)-[:LOCATED_IN]->(loc)

// 3. Link the episodic turn to the entities it mentioned
MERGE (t:Turn {id: "t-1"})
MERGE (t)-[:MENTIONED]->(a)
MERGE (t)-[:MENTIONED]->(org)

The word "software engineer" is an attribute, so give the edge a property: MERGE (a)-[:WORKS_AT {role: "software engineer"}]->(org). Now query facts about one entity without knowing the paths in advance:

MATCH (a:Entity {name: "Alice Johnson"})-[r]-(other)
RETURN type(r) AS fact, other.name AS about
// fact = WORKS_AT, about = Acme Corp
// (traversed from Alice — no text chunk contained this pair as a sentence)

Which of these belongs in semantic memory?

Do it

  1. Pick one real message from your cockpit data, e.g. "Alice Johnson is a software engineer at Acme Corp in London." Ask an LLM to return a JSON list of entities and typed relationships — that extraction step is LLM-assisted and that is expected.
  2. Verify the extraction by hand before writing. Rule 12: you must be able to explain every node and edge. Fix wrong or invented facts yourself; never MERGE unverified LLM output.
  3. Run the MERGE block above in FalkorDB Browser (fill in the real names/roles from your message).
  4. Run the MERGE block a second time. Expected result: no new nodes, no new edges — MERGE kept it idempotent.
  5. Run the MATCH query. Expected output: one row per fact edge touching your entity, e.g. WORKS_AT | Acme Corp. You now have a fact graph built from a single message.
  6. Add an index so larger writes stay fast: CREATE INDEX FOR (e:Entity) ON (e.name). The FalkorDB guide warns to index "node properties used in MERGE operations … to prevent full-graph scans during writes."
