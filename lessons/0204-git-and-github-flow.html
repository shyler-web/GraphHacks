Git & GitHub as Agent Memory

Submission rule 10 requires a public repo. But the repo is more than a delivery box: the commit history is the one memory every future session — human or agent — can read from cold.

By the end you can commit a verified unit and push it to a public GitHub remote, after a secret check, evidenced by git log --oneline showing your commit and git push reporting the branch is up to date.

Why this matters

You are solo, switching between the graph database, the Cypher, the cockpit UI, and deployment. 10xdev.blog names the core failure: developers "think the AI remembers what it decided. It doesn't" — every new session "starts cold" and "will re-derive the decision, sometimes arriving at a different answer." The fix is not notes but git as the agent's long-term memory: commit messages carrying what was built, the decision, why, and the exit evidence.

Lesson 0110 is the theory — write every commit as a briefing for a capable teammate with no context. This lesson is the mechanics: the exact commands, what to push, and the safety check that keeps secrets out of a public repo.

Work in small, verified units. The instant a unit passes its exit criterion, commit and push — do not batch. The history is the briefing; an unpushed commit is not yet memory the submission can see.

The idea

Git has three stages: your working files, the staging area (git add), and the commit (a snapshot). Then a remote — the GitHub copy — receives it with git push. GitHub's quickstart is the canonical path: create the repo, commit, and git push --set-upstream origin HEAD (equivalent to git push -u origin main), which links your local branch to the remote so later pushes are just git push (GitHub Quickstart).

git init                       # start history in this folder (already done)
git add                 # stage exactly what changed
git commit -m "…briefing…"     # snapshot with a message for future-you
# create the repo on github.com (public), then:
git remote add origin git@github.com:<you>/<repo>.git
git push -u origin main        # first push; -u remembers the remote

Write the commit message in the shape 0110 taught — what changed · the decision + why · the evidence:

commit: "wip" — no decision, no evidence. Next session re-derives everything.

feat(memory): persist Turns to FalkorDB via MERGE; decision: one graph per tenant (D2); verify: npm run health = 2

What to push, what to never push

Push (the source of truth)Never push (ignored by .gitignore)
source (src/), lessons/, reference/, AGENTS.md, .opencode/, PROGRESS.md, queries.cypher, .env.example, graphify-out/graph.json .env and any key/token, node_modules/, the graphify cache (graphify-out/cache/), *.key/*.pem, build output

.gitignore is a file listing paths git pretends not to see — it already excludes .env and .env.* (while keeping !.env.example) and the graphify cache. But .gitignore only stops untracked files. If a secret was ever added, it is still tracked. So run the secret check before every commit:

git diff --cached      # review exactly what is staged — no keys, no .env
Three hard rules. Commit per verified unit; push after each verified commit (the public repo is rule 10's source of truth, so keep it current). Never force-push — it erases history a future session depends on. Never commit broken code as "done" — if it is not verified, it is not finished.

What must never be pushed to the public repo?

Commit and push one verified unit, safely.

  1. Confirm a unit passed its exit criterion. Check status: git status.
  2. Stage it: git add <paths> (stage only what you intend).
  3. Secret check: git diff --cached. Expected: the diff shows your source and docs, and no .env, keys, or tokens.
  4. Commit with a briefing message: git commit -m "feat(memory): … what / decision + why / verify: …". Expected: one commit, with your message on the first line.
  5. Push: git push. Expected: Everything up-to-date or a summary of the uploaded objects, with no error.
  6. Verify memory is visible: git log --oneline -10. Expected: your commit at the top.
