Lesson 0008 · Track 02 — Agent Memory and Coordination

Per-Tenant Isolation with Multi-Graph

Give every user or tenant their own isolated memory graph inside one FalkorDB instance — no separate deployment, no leaked memory.

By the end you can select a separate graph per tenant, write agent memory into it, and prove a query in tenant B returns nothing from tenant A, evidenced by an empty result set for B and a populated one for A.

Why this matters

"Separate memory per user or tenant" is a Track 02 key-focus point. If every agent writes into one graph, one tenant's memory becomes another tenant's context — a correctness and privacy bug. FalkorDB's multi-graph / multi-tenant topology lets each tenant own an isolated graph in the same instance.

The idea

FalkorDB "lets you run multiple isolated graph databases within a single FalkorDB instance. Each tenant operates independently with its own data, queries, and access controls while sharing the underlying infrastructure" — in practice you "create distinct graph databases for each customer or project."1 You pick the graph by name at connection/selection time, then run ordinary Cypher against it. The Python client uses select_graph(name) and the Node.js client uses selectGraph(name).2

// Python — one tenant, isolated by graph name
from falkordb import FalkorDB
db = FalkorDB(host='localhost', port=6379)

tenant_a = db.select_graph('tenant_alice')   # separate graph
tenant_b = db.select_graph('tenant_bob')     # separate graph

tenant_a.query("MERGE (u:User {id:'alice'}) "
               "MERGE (u)-[:REMEMBERS]->(m:Memory {text:'prefers dark mode'})")

print(tenant_b.query("MATCH (m:Memory) RETURN m.text").result_set)  # []

// Node.js equivalent
// const graph = db.selectGraph('tenant_alice')

Same query, run against each graph, sees only that graph — that is the isolation. A graph is created lazily by its first write, and db.list_graphs() (Python) / db.list() (Node) / GRAPH.LIST enumerates them.3

Trade-off. One-graph-per-tenant buys isolation and operational simplicity (one instance, no per-tenant deploy, no tenant filter clause). It costs cross-tenant analytics: you cannot MATCH across graphs in a single query, so a "all users" report must loop over graphs or aggregate into a shared graph. For agent memory, isolation wins.

Why is one-graph-per-tenant usually better than one big graph with a tenantId property?

Do it

  1. Ensure FalkorDB is running (from Lesson 0001): docker run -p 6379:6379 -p 3000:3000 -it --rm falkordb/falkordb:latest. Expected: container logs "Ready to accept connections" on port 6379.
  2. Install the Python client: pip install falkordb. Expected: Successfully installed falkordb.
  3. Save and run the snippet from "The idea." Expected: the final line prints [] — tenant B cannot see tenant A's memory.
  4. Prove A still has it — add print(tenant_a.query("MATCH (m:Memory) RETURN m.text").result_set) and rerun. Expected: [['prefers dark mode']].
  5. List the isolated graphs: print(db.list_graphs()). Expected: a list including tenant_alice and tenant_bob (plus any telemetry graph).
