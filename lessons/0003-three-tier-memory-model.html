The Three-Tier Memory Model

One connected graph holds episodic, semantic, and procedural memory — and that single model is exactly what Track 02's first key-focus point asks you to demonstrate.

By the end you can draw and name your own graph data model, evidenced by a node/edge sketch covering all three memory tiers and the edges that link them.

← Curriculum Prev Next → Graph data model

Why this matters

Track 02's first key-focus point is literally "episodic, semantic, and procedural memory." Your submission has to show all three working — not because a rubric says so, but because they answer three different questions: what happened, what is true, and how to act. Getting the model right now means every later lesson (history, facts, playbooks, handoffs, tenant isolation) is just filling in a node type you already named.

The idea

Per FalkorDB's guide to graph-backed agents, agent memory divides into three functional categories, each mapping to graph structures differently [1]:

  • Episodic memory — a record of specific past interactions, stored as timestamped event nodes linked to the entities involved, so an agent can recall "what happened last time."
  • Semantic memory — durable factual knowledge about the domain: entities, attributes, and their relationships, independent of any single interaction.
  • Procedural memory — stored tool-use patterns and successful query strategies, represented as reusable workflow subgraphs an agent can re-execute.

The key insight is the three-tier memory model: these are not three separate stores. They are three node families in one connected graph, joined by typed edges (relationships). The edges are the point — a Turn (episodic) that MENTIONS an Entity (semantic) or USES a Tool (procedural) is what turns three piles of data into memory an agent can traverse.

 EPISODIC                         SEMANTIC
 (:User)─[:HAS_SESSION]→(:Session)      (:Entity)─[:RELATES_TO]→(:Entity)
    │                        │              ▲
    │                 [:HAS_TURN]           │ [:MENTIONS]
    ▼                        ▼               │
 (:User)──────────────→ (:Turn)─────────────┘
                             │
                             │ [:USED]            PROCEDURAL
                             ▼
                          (:Tool)─────────────→ (:Workflow)  [:PART_OF]

 Linking edges = the whole game:
   Turn -[:MENTIONS]→ Entity   (episodic ↔ semantic)
   Turn -[:USED]→ Tool         (episodic ↔ procedural)
   Entity -[:RELATES_TO]→ Entity, Tool -[:PART_OF]→ Workflow

Write it with MERGE. Timestamped Turn nodes are created fresh; User, Entity, Tool nodes are matched-or-created so repeated mentions don't duplicate them. That is why FalkorDB's episodic-memory example uses MERGE (u:User …) before CREATE (e:Episode …) [1].

Your agent stores: "On 14:02, user u-1234 asked about auth-service dependencies." Which tier is this?

The User -[:USED]→ Tool -[:PART_OF]→ Workflow subgraph that your agent replays for "summarize a repo" is which tier?

Do it

  1. Open a blank file or drawing tool and sketch three columns: Episode, Semantics, Procedures.
  2. Under Episodes place nodes User, Session, Turn. Under Semantics place Entity, Fact. Under Procedures place Tool, Workflow.
  3. Draw the linking edges and label each direction: User-[:HAS_SESSION]->Session, Session-[:HAS_TURN]->Turn, Turn-[:MENTIONS]->Entity, Entity-[:RELATES_TO]->Entity, Turn-[:USED]->Tool, Tool-[:PART_OF]->Workflow.
  4. Circle the two edges that cross a tier boundary — those are what make it one connected graph, not three stores. Keep this sketch; Lesson 0004 onward fills it in, and it becomes the graph data model in your README.
  5. Next: open reference/graph-schema.html and compare your sketch against the canonical model.
