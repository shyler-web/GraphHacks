Lesson 0007 · Track 02 — Agent Memory and Coordination

Multi-Agent Coordination and Handoffs

Keep your 4-agent squad coordinated by writing every transfer into the graph as a handoff record, so the next agent reads what happened instead of being told it in a message it might never receive.

By the end you can record a handoff with MERGE and reconstruct the ledger a receiving agent reads with MATCH, evidenced by one ordered row per transfer, each carrying reason, timestamp, and artifact.

Why this matters

Track 02 asks for handoffs between agents and shared state. A Handoff is "the transfer of state and responsibility from one agent to another, recorded in the graph so the receiving agent knows what was done and why" (GLOSSARY). Note the trap word: a handoff is not message passing when the state is not persisted.

Your repo already names a 4-Agent squad (VibeArchitect L0–L1, FullStackBuilder L2–L3, SeniorAuditor L4, PrincipalResearcher L5) and a handoff ledger. This lesson makes that ledger real: an ordered, queryable record of every transfer, readable by the next agent on the next session.

The idea

A squad needs three things in the graph: an Agent node per squad member, a Handoff record per transfer, and shared memory nodes both agents read and write. The handoff carries only what coordinates the transfer — reason, at, artifact, status — not the sender's whole context. That is the line between an edge (relationship) and a prompt.

Persisted state beats passing messages because a message is a snapshot that disappears with the process, while a graph record is durable and reachable: the next agent, or a teammate, can traverse it, filter it, and show the path (WeMakeDevs). The handoff edge is written with MERGE, "the Cypher clause that matches a pattern or creates it if it does not exist, the basis of idempotent memory writes" (FalkorDB Cypher docs).

// Pattern shape
//   (:Agent {id}) -[:HANDED_TO {id, at, reason, artifact, status}]-> (:Agent {id})
//   (:Agent) -[:PRODUCED]-> (:Finding)   // shared memory one agent writes
//   (:Agent) -[:READS]->    (:Finding)   // and the next agent reads

MERGE (from:Agent {id: 'vibe-architect'})
MERGE (to:Agent   {id: 'fullstack-builder'})
MERGE (from)-[h:HANDED_TO {id: 'h-0001'}]->(to)
  SET h.at       = $at,
      h.reason   = 'Spec frozen; implement endpoints',
      h.artifact = 'openapi.yaml@v3',
      h.status   = 'PENDING'
RETURN from.id AS from, to.id AS to, h.reason AS reason

Do it

  1. Create the two agents and record one handoff. Pass the timestamp as a parameter ($at) rather than calling a function, so it matches the Unix-epoch convention in your graph data model. Run it in the FalkorDB Browser or via graph.query(...), substituting {at: <epoch>}.

    MERGE (from:Agent {id: 'vibe-architect'})
  ON CREATE SET from.name = 'VibeArchitect', from.role = 'L0-L1'
MERGE (to:Agent {id: 'fullstack-builder'})
  ON CREATE SET to.name = 'FullStackBuilder', to.role = 'L2-L3'
MERGE (from)-[h:HANDED_TO {id: 'h-0001'}]->(to)
  SET h.at       = $at,
      h.reason   = 'Spec frozen; implement endpoints',
      h.artifact = 'openapi.yaml@v3',
      h.status   = 'PENDING'
RETURN from.id AS from, to.id AS to, h.reason AS reason

    Expected (one row): vibe-architect | fullstack-builder | Spec frozen; implement endpoints. Re-run it with the same h-0001 — still one row, because MERGE is idempotent and keys on the handoff id.

  2. Add a shared memory node both agents touch — the sender writes it (PRODUCED), the receiver reads it (READS). This is the "shared state" half of the requirement.

    MERGE (from:Agent {id: 'vibe-architect'})
MERGE (to:Agent   {id: 'fullstack-builder'})
MERGE (f:Finding {id: 'f-0001'})
  ON CREATE SET f.text = 'Auth uses short-lived JWTs', f.at = $at
MERGE (from)-[:PRODUCED]->(f)
MERGE (to)-[:READS]->(f)
RETURN f.text AS shared_finding

    Expected: Auth uses short-lived JWTs. Both agents point at the same node, so neither needs the fact pasted into a prompt.

  3. Reconstruct "what happened so far" for the receiving agent. This is the query handleRunMultiAgentPrompt should run before it acts — the ledger, oldest first.

    MATCH (prev:Agent)-[h:HANDED_TO]->(me:Agent {id: 'fullstack-builder'})
RETURN prev.name AS handoff_from, h.at AS at, h.reason AS reason, h.artifact AS artifact
ORDER BY h.at ASC

    Expected (one row for the graph so far):

    handoff_fromatreasonartifact
    VibeArchitect1729000000Spec frozen; implement endpointsopenapi.yaml@v3

    Point {id: ...} at 'senior-auditor' instead and you get zero rows — proving the ledger is per-receiver, not a global dump.

  4. See the whole squad. Drop the receiver filter to read the full ledger — this is what you show on the cockpit's handoff panel.

    MATCH (from:Agent)-[h:HANDED_TO]->(to:Agent)
RETURN from.name AS from, to.name AS to, h.reason AS reason, h.status AS status
ORDER BY h.at ASC

    Every transfer is one row, in time order. That is your persisted handoff ledger: the next agent reads it, and so can a judge.

Debug tip: if the ledger is empty, check the edge property you keyed on. MERGE (from)-[h:HANDED_TO {id: 'h-0001'}]->(to) only matches a relationship that already has that exact id. A typo silently creates a second edge instead of reusing one — inspect the graph in the Browser, not the terminal.

FalkorDB documents agent memory and multi-tenant graphs, but no single trusted source yet defines a shared multi-agent handoff pattern over FalkorDB — that is an open gap (see RESOURCES.md). This edge-shaped ledger (handoff as a property-bearing [:HANDED_TO] edge, with shared memory as PRODUCED/READS) is your design. It is also a stronger fit than the node-based :Handoff variant in your schema when the transfer itself is the event you want to order; if you later need a handoff to target an entity, promote it to a node with FROM_AGENT/TO_AGENT.
