Cypher for Memory

Why this matters

Agent memory is the persistent, queryable state your agent reads and writes across sessions. In this project that state lives in FalkorDB, and Cypher is how the code touches it. Every Track 02 key-focus point — episodic memory, semantic memory, handoffs, concurrency, per-tenant isolation — is ultimately a Cypher pattern match or update. Learn these five clauses and you can read the simulated backend in src/graphsync_multi_agent_falkordb_memory_cockpit.tsx and tell exactly what each query is meant to do.

The idea

A graph database stores data as nodes and edges (relationships). Cypher draws patterns as ASCII art, then matches or creates them:

()-[]->()   // node -> relationship -> node
(n:Session)             // a node variable n, labelled Session
(a)-->(b)               // a to b, any relationship
(u:User)-[:HAS]->(s)    // u HAS a relationship of type HAS to s

Five clauses carry almost all memory work. FalkorDB supports them as standard OpenCypher clauses:

ClauseWhat it does for memory
CREATEAlways adds new nodes/edges. Re-running it duplicates. Use only for truly new events.
MERGEMatches the pattern, or creates it if absent. The memory-write primitive, because it is idempotent — safe to re-run.
MATCHFinds existing patterns. The memory-read primitive.
WHEREFilters a MATCH by property or comparison.
RETURNProjects what the query gives back to the agent.

Why MERGE is the memory-write primitive

A memory write often retries — an agent restarts, a request replays, a demo is run twice. With CREATE, every re-run adds a second copy of the same fact. With MERGE, the second run finds the first and creates nothing. That is idempotent upsert, and it is why the memory layer of this project should never write a fact with CREATE.

// CREATE — run twice, get two nodes:
CREATE (:Fact {id: 'user-likes-cypher', text: 'Alice likes Cypher'})

// MERGE — run twice, still one node:
MERGE (:Fact {id: 'user-likes-cypher', text: 'Alice likes Cypher'})

One write, one read

Write a tiny piece of episodic memory — a session node linked to a user — using one MERGE per element so no duplicates appear:

MERGE (u:User {id: 'alice'})
MERGE (s:Session {id: 's-001'})
MERGE (u)-[:HAS_SESSION]->(s)

Read it back:

MATCH (u:User {id: 'alice'})-[:HAS_SESSION]->(s:Session)
RETURN u.id AS user, s.id AS session

You are writing a fact that may be submitted more than once because the agent retries. Which clause should you use?

Do it

  1. Make sure your FalkorDB instance from Lesson 0001 is running, then open its CLI: 
    docker exec -it falkordb redis-cli
    You should see the prompt 127.0.0.1:6379>.
  2. Write the memory into a graph named memory with MERGE: 
    GRAPH.QUERY memory "MERGE (u:User {id:'alice'}) MERGE (s:Session {id:'s-001'}) MERGE (u)-[:HAS_SESSION]->(s)"
    Expected: a result line ending in (0.00s), with Nodes created: 2 and Relationships created: 1.
  3. Run the exact same command again. Expected this time: Nodes created: 0, Relationships created: 0 — MERGE matched instead of duplicating.
  4. Read the memory back: 
    GRAPH.QUERY memory "MATCH (u:User {id:'alice'})-[:HAS_SESSION]->(s:Session) RETURN u.id, s.id"
    Expected: a header row u.id, s.id and one row alice, s-001. That is the win.
  5. Prove the difference: GRAPH.QUERY memory "CREATE (:Fact {id:'x'})" twice, then MATCH (f:Fact) RETURN count(f) — you get 2. Swap CREATE for MERGE and the count stays 1.
