Lesson 0109 · The Engineer's Prompt

Compartmentalize Roles & Autonomy

One session for planning, coding, testing, and debugging makes the agent improvise in layers it should never touch. Split the work into roles with hard boundaries, then match how much rope each role gets to the risk of the task.

By the end you can assign one task to a bounded builder session and review it in a separate reader session, and name the autonomy tier for each, evidenced by a builder that stopped at its first blocker with an issue report and a review pass that only read.

Why this matters

Your Track 02 system has many moving parts — a graph model, Cypher writes, a handoff ledger, per-tenant isolation, a React cockpit. If you hand all of that to one long session, the agent accumulates context from everything it has done, "its role blurs," and "it starts fixing code in layers it shouldn't touch" ([10xdev, #4](https://10xdev.blog/7-things-developers-get-wrong-about-ai-agents-2026/)). The bug you will chase at 2 a.m. is a fix applied two modules away from the fault.

You already run role agents in opencode (researcher, planner, builder, reviewer, debugger, gitter). This lesson is about giving them boundaries and the right amount of autonomy — the engineering judgment that makes those sessions useful instead of noisy.

Give each role a hard boundary: a builder that stops at the first blocker and reports it, a fixer that only touches core, a reviewer that only reads. Then pick the autonomy tier before the task, not after.

The idea

The pattern that replaces the one mega-session is two roles with structurally separated work. The builder "builds against your system … stops at the first blocker and reports it. Never touches core code." The fixer "reads blocker reports, fixes core code. Never touches the app being built" ([10xdev, #4](https://10xdev.blog/7-things-developers-get-wrong-about-ai-agents-2026/)). The separation is not tidiness — a builder that cannot rationalize a bug away "experiences bugs the way a real user would," producing precise, actionable reports. In your project that report is also a handoff: the same reason/artifact record lesson 0007 puts in the graph.

Autonomy is the second dial. Match oversight to risk: Tier 1 interactive — the agent proposes, you approve, "best for novel decisions, architecture, anything where the wrong choice is expensive"; Tier 2 bounded sprint — the agent works independently and "reports back at a defined checkpoint," best for implementing a spec you already wrote; Tier 3 unattended — it runs alone and you review the result, "best for purely mechanical tasks" ([10xdev, #5](https://10xdev.blog/7-things-developers-get-wrong-about-ai-agents-2026/)). A bigger framework says the same thing in five levels and warns that "more autonomy is not always better" — the good pattern is to let the agent explore low-risk work autonomously but "drop to [supervised] … for high-stakes actions" ([BigData Boutique](https://bigdataboutique.com/blog/everything-you-need-to-know-before-building-ai-agents)).

Run one task as a builder, then review it in a separate pass.

  1. Pick one small Track 02 task and write its role card: the single file it may touch, the autonomy tier, the checkpoint, and the exact stop-and-report rule.
  2. Run it in a fresh opencode session as the builder. If it hits a blocker, keep the issue report it wrote — do not fix it yourself in the same session.
  3. Open a second session as the reviewer with read-only instructions: find problems, change nothing. Compare the two outputs — what did the separated review catch that the builder missed?
