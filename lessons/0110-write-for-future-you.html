Lesson 0110 · The Engineer's Prompt

Write for Future-You & Ask Like a Senior

Every new agent session starts cold: it knows nothing about the decision you made yesterday. Two habits fix that — a commit history written as a briefing, and questions sharp enough that a helper can act on the first try.

By the end you can commit a design decision the next session can recover from, and write a bug report a stranger could act on, evidenced by one decision-bearing commit and one sharp report in your repo.

Why this matters

Track 02 is four days long and you are switching between the graph model, the Cypher, the cockpit UI, and the deployment. You will forget why you chose a [:HANDED_TO] edge instead of a property, and so will the agent. If that decision is not in the repo, the next session re-derives it — often differently — and the system drifts.

Rule 12 asks you to explain your architecture and decisions on demand. A repo that remembers is the same skill, recorded.

Every new session starts cold. Write every commit message and every question as if briefing a capable teammate who has no prior context — because that is exactly who reads it.

The idea

10xdev.blog names the failure directly: developers "think the AI remembers what it decided. It doesn't." The topic has no memory of the conversation three days ago where you picked your auth approach; it "will re-derive the decision, sometimes arriving at a different answer." The fix is not session logs or sticky notes but the git history — commit messages that carry what was built, the design decision, why, and the exit evidence, not just “fixed bug.”

So open every session with the same four-command protocol, reading the repo as the agent's long-term memory:

git log --oneline -10           # what happened recently
git log --grep="decision" -5    # what was decided and why
git diff HEAD~5 --stat          # what files changed
<health check command>          # current system status

Your health check for this project is the FalkorDB one-liner — e.g. docker exec falkordb redis-cli GRAPH.LIST — proving the instance is up before you ask for anything.

The second habit is asking. SiliconWit shows that a good bug report is "itself a debugging tool," and it has a fixed shape: what you expected, what actually happened, steps to reproduce, and what you already tried. Writing it forces the precision that a vague plea skips. When you are stuck, the same source sets the clock: after 30 minutes without progress, explain the problem out loud — the rubber-duck effect "forces you to examine your assumptions"; after half a day, bring a fresh reader, stating what you tried, what you ruled out, and your best hypothesis.

commit: "wip" — then ask "the graph query doesn't work, can you fix it?"

commit: "feat(memory): episodic turns via MERGE on (:Turn) — decision: MERGE not CREATE so replays stay idempotent (reason: retries duplicate history). exit: 1 round-trip test green."

Ask: "recall_turns returns [] after write_turn succeeds. Expected the turn back. Reproduce: docker exec falkordb redis-cli GRAPH.QUERY tenant:42 'MATCH (t:Turn) RETURN t' returns the node, so the write is fine. Tried: matching by session id, by user id; ruled out MERGE. Best hypothesis: recall matches on topic, which write never sets."

Which message lets a helper act on the first try?

Make your first meaningful commit, then write one sharp report.

  1. Init the repo and push: git init, git add -A, commit the foundation, then create the GitHub remote and git push -u origin main.
  2. Commit one real design decision with a message that briefs the next session: what was built, the decision, why, and the evidence. Keep the word decision in it so git log --grep="decision" finds it.
  3. Pick one problem that is currently blocking you and write a four-part report — expected, observed, steps to reproduce, what you tried. Paste it to your teacher (or the FalkorDB Discord) instead of describing it loosely.
