Define Done: Spec Cards

"Wire up the memory" is a wish. A five-line spec card turns it into a task the AI can finish correctly on the first pass — and proves it when it says "done."

By the end you can write a 5-part spec card for one task in your cockpit, evidenced by a copy-pasteable card whose exit criterion is a specific, verifiable check.

← Curriculum Prompt playbook Deriving exit criteria Prev Next →
Before you prompt, write the exit criterion first. If you cannot name the exact check that proves the task is done, you are not ready to hand it to an agent.

The idea

An under-specified task fails three ways: the agent does too little (stops at the first ambiguity), too much (invents requirements), or something technically correct that is wrong for your context. The fix is not a better-worded prompt — it is a spec. The 2026 practice is spec-driven development: a mini-spec for every task, with five parts.

"Build the login feature" is not a task. It's a wish.

The five parts: (1) what it builds — one sentence. (2) exit criterion — a specific, verifiable check, never "it works." (3) out of scope — what it must not do. (4) locked decisions — choices the agent cannot reopen. (5) verification step — how the agent proves it.

The exit criterion is the highest-leverage line. "Feature works" changes with whoever is looking. "The login form submits, receives a session cookie, and redirects to /dashboard" cannot be argued with. Teams using spec-driven tasks report 3–10× higher first-pass success rates because the agent never has to guess what done looks like.

"Wire up the memory so the cockpit uses FalkorDB."

What: One real read path from the cockpit to FalkorDB.
Exit: curl localhost:5173/api/graph/nodes returns JSON containing a node I created in the FalkorDB browser.
Out of scope: writes, auth, styling.
Locked: Vite dev-server plugin, port 6379, graph name graphsync_user1_ai_avatar_saas.
Verify: run the curl, paste the output.
