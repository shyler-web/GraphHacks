Explainable Answers: Show the Path

Return the path — not just the answer — so your agent can show the judge exactly how it got there.

By the end you can return a path from Cypher, expand it into the nodes and edges along the way, find "how are these connected" with shortestPath, and emit an answer payload that ships the answer, its subgraph, and its sources — evidenced by a traced, sourced answer you can show in the demo.

Why this matters

Track 02 asks for answers with clear sources, and the hackathon brief repeats it: explainable results and show the path behind an answer. A judge scores your demo on whether they can trust it. A bare answer is a black box; an answer plus the Edge (relationship) trail that produced it is auditable. Your liveCypherQuery UI already runs Cypher — this lesson makes it return the trail too, so the Bubble-Up Alerting view can render why an alert fired, not just that it fired.

The idea

A Cypher query normally returns values. If you bind a whole pattern to a variable, it returns a path — the ordered sequence of Nodes and Edges that matched:

MATCH p=(a)-[:...]->(b) RETURN p

A path is one value, but you can unpack it with the path functions (FalkorDB supports these):

  • nodes(p) — the list of nodes along the path.
  • relationships(p) — the list of edges along the path.
  • length(p) — the number of edges (hops) in the path.

For "how are these two things connected?", the pattern is unbounded and you ask for the shortest route:

MATCH (a:Entity {name: 'Alice'}), (b:Entity {name: 'Billing'})
WITH shortestPath((a)-[*]->(b)) AS p
RETURN length(p), [n IN nodes(p) | n.name] AS pathNodes

The shortestPath argument is a traversal pattern whose endpoints must already be resolved, and no property filters may appear inside it. If there is more than one shortest path, only one is returned; use allShortestPaths when the trail could matter more than one route.

Provenance: Episodic memory is timestamped event nodes. To make an answer sourced, carry the event node's ts (and the node it came from) back up the path instead of discarding it. That timestamp is your citation.

Why does returning the path (not just the answer) matter most for judging?

Do it

  1. Return a whole path instead of a value. Bind the pattern to p and return it: 
    MATCH p=(:Session)-[:HAS_TURN]->(t:Turn)-[:MENTIONS]->(e:Entity)
WHERE e.name = 'Billing'
RETURN p
    Expected: one row per matching trail, where column p holds the full path value (nodes + edges), not a scalar.
  2. Unpack the path into renderable pieces so the UI can draw it: 
    MATCH p=(:Session)-[:HAS_TURN]->(t:Turn)-[:MENTIONS]->(e:Entity)
WHERE e.name = 'Billing'
RETURN [n IN nodes(p) | n.name] AS nodes,
       [r IN relationships(p) | type(r)] AS edges,
       length(p) AS hops
    Expected: nodes is a list of names, edges is a list of edge types in order, hops is an integer count of edges.
  3. Ask "how are these connected?" with the shortest path and carry provenance: 
    MATCH (a:Entity {name: 'Alice'}), (b:Entity {name: 'Billing'})
WITH shortestPath((a)-[*]->(b)) AS p
RETURN length(p) AS hops,
       [n IN nodes(p) | n.name] AS pathNodes,
       [t IN nodes(p) WHERE t.ts IS NOT NULL | {name: t.name, ts: t.ts}] AS sources
    Expected (mirrors the docs' A → D → F → G example): a hop count, the ordered node names, and the subset of nodes carrying a timestamp — your citations.
  4. Shape the agent's answer payload so the cockpit can render answer + subgraph + sources together: 
    {
  "answer": "Billing is why the alert fired.",
  "hops": 3,
  "subgraph": { "nodes": ["Alice", "Invoice", "Billing"], "edges": ["MENTIONS", "ABOUT"] },
  "sources": [ { "node": "Turn:8123", "ts": 1760000000000 } ]
}
    Feed subgraph.nodes / subgraph.edges to your liveCypherQuery renderer and sources to the citations panel. The judge now sees the answer and the trail that justifies it.
