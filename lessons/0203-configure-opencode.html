Configure opencode for the Build

opencode is not one assistant — it is a small team with a shared rulebook. The repo already defines the rules, the roles, and the guardrails; this lesson is how to drive them instead of fighting them.

By the end you can invoke the right subagent or skill for a task and explain why AGENTS.md is injected every session, evidenced by a task you routed to @builder, then @gitter, by naming the role each time.

Why this matters

You are solo, so opencode is your whole team. The repo's config is not decoration — it is the mechanism that keeps every session aligned to the same locked decisions, the same exit criterion, and the same secret rules, whether you or a future model starts the session. Using it well is the difference between an agent that ships a vertical slice and one that improvises across layers it should never touch (lesson 0109).

AGENTS.md — read every session

opencode reads your project's AGENTS.md and includes it in the model's context automatically; the first matching file wins, and opencode.json's instructions array is combined with it (rules docs). This repo injects three files — AGENTS.md, docs/decisions.md, PROGRESS.md — so every session starts knowing the context budget's ALWAYS bucket (lesson 0104).

The ALWAYS block is the load-bearing part: the binding rules (Track 02, real FalkorDB, deadline), the goal + exit criterion (stopping FalkorDB visibly breaks the app), the locked decisions (D1–D5), and the health check (npm run health). Read it before every task; never reopen a locked decision without recording a new one.

Precedence, in one line: project AGENTS.md → global ~/.config/opencode/AGENTS.md → Claude-compat ~/.claude/CLAUDE.md. The first match in each category wins (rules docs).

The subagents — who to @mention

Subagents are specialized assistants a primary agent can invoke, or you can invoke manually with @mention (agents docs). Each file in .opencode/agent/ is one role; its frontmatter sets permissions, so a reviewer literally cannot edit. Use them per the roles/autonomy split from lesson 0109.

SubagentUse whenBoundary
@researcherYou need current, cited facts (FalkorDB, MCP, Tavily, agent-memory patterns)Read-only; cites every claim
@teacherAuthoring or revising a lesson or reference pageWrites lessons/, reference/
@plannerScoping a task — turn a wish into a spec card / decision recordPlans, does not code
@builderImplementing one spec card against FalkorDBFull edit; stops at first blocker
@reviewerBefore committing — correctness, rule-3 "real work", secretsRead-only; severity-ordered findings
@debuggerSomething breaks, hangs, or misbehavesReproduces before proposing a fix
@gitterA milestone passed its exit criterion, ready to commit + pushRuns verify, then git; never commits broken/secret code
@graphify-keeperAnswering a codebase question, or after significant changesOwns the graphify graph

"Fix the memory loading and commit it."

"@builder implement the spec card: write_turn round-trips a turn by id. @reviewer check it after. @gitter commit + push once npm run health passes."

Skills — loaded on demand

Skills are reusable instructions opencode discovers from .opencode/skills/<name>/SKILL.md and loads only when needed via the skill tool (skills docs). This repo has three:

SkillLoads when
prompt-playbookYou are about to ask the AI to build/fix/change something — write the 5-line spec card first
verify-changeAfter any state-changing step — run the exit criterion immediately, never batch
track02-buildStarting or resuming build work — stack, build order, the five key-focus points

They live on demand so they cost nothing until relevant — the ON DEMAND bucket from lesson 0104.

opencode.json — rules, guardrails, tools

The project config sets three things you should know before you run anything (config docs):

  • Permissions: git, npm, npx, docker, graphify, ls are allow; everything else ask. Reading .env* and editing secrets (**/.env, *.pem, *.key) are deny.
  • MCP servers: falkordb (graph tools) and tavily (web search) — keys are read from env via {env:...}, never hard-coded.
  • Instructions: the three ALWAYS files above, combined with AGENTS.md.

The graphify rule — query first, rebuild after

Before exploring the codebase, query the graph: graphify query "<question>". Only read files the graph points to. After significant changes, graphify update .. The graph at graphify-out/graph.json is the project's durable, model-agnostic memory — the reason you can switch models and the next session rebuilds context from the graph instead of re-reading the repo.

Name the role before you type. Read-only question → @researcher / @reviewer. Plan → @planner. Build one slice → @builder. Commit verified work → @gitter. And query graphify before reading files.

Do it

  1. Open this repo in opencode and type @ — confirm all eight project subagents appear in the mention menu.
  2. Ask a codebase question through the graph first: @graphify-keeper "where is memory loaded?". Note it points to files instead of dumping the repo.
  3. Route one real task: @builder a small spec card, then @reviewer it, then @gitter the verified result.

Which subagent commits verified work and pushes it?

Pick the subagent for each task — say the role before you type it:

  1. "Is the FalkorDB MCP server still the current recommended way to expose graph tools?" → which subagent?
  2. "Turn 'make tenant switching work' into a spec card with an exit criterion." → which subagent?
  3. "The dev server hangs after I add the read route." → which subagent?

Answers: @researcher · @planner · @debugger.
