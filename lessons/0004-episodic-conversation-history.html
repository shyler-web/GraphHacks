Episodic Memory: Conversation History

Persist each interaction as timestamped Nodes in FalkorDB so your agent recalls the right past turns across sessions instead of replaying everything.

By the end you can write one conversation turn with MERGE and recall a user's last N turns about a topic, evidenced by the recall query returning those turns newest-first.

Why this matters

Two Track 02 key-focus points are episodic memory and persistent conversation history. Your cockpit's backend is simulated today, so it "forgets" between reloads. This lesson replaces the simulation with a real graph write — the first piece of agent memory your demo can point at.

The idea

Episodic memory is a record of specific past interactions, stored as timestamped event Nodes linked to the entities involved. FalkorDB's canonical example writes exactly that: a MERGEd User and Topic, plus a created Episode carrying a timestamp, connected by Edge (relationship)s PARTICIPATED and ABOUT.[1] We extend the same shape with an explicit Session and Turn so history is grouped by conversation, not one flat pile.

Model (all Cypher, all in one graph):

(:User)-[:PARTICIPATED]->(:Session)-[:HAS_TURN]->(:Turn)-[:ABOUT]->(:Topic)
                                           (:Turn)-[:MENTIONS]->(:Entity)

Why this beats replaying a raw transcript: replaying the whole chat log into the prompt is unbounded — it grows every turn, wastes context, and still can't answer "what did this user ask about auth three sessions ago?" A graph query is bounded, targeted, and traversable. You ask for one user, one topic, the newest N turns — and you can walk from a recalled turn to the entities it touched. That relational recall is the whole reason a graph layer exists instead of a vector store.[2]

Write one turn idempotently — MERGE on identity, ON CREATE SET for the data, so re-running never duplicates:

MERGE (u:User {id:'u-1234'})
MERGE (s:Session {id:'s-01'})
MERGE (t:Turn {id:'t-01'})
ON CREATE SET t.timestamp=1715300010, t.role='user',
              t.text='Which services break if auth goes down?'
MERGE (u)-[:PARTICIPATED]->(s)
MERGE (s)-[:HAS_TURN]->(t)
MERGE (topic:Topic {name:'auth-service-dependencies'})
MERGE (t)-[:ABOUT]->(topic)

Recall the last N turns for one user about one topic. This is the query your "memory" panel and your LLM context-builder share:

MATCH (u:User {id:'u-1234'})-[:PARTICIPATED]->(s:Session)
      -[:HAS_TURN]->(t:Turn)-[:ABOUT]->(topic:Topic {name:'auth-service-dependencies'})
RETURN t.text AS text, t.timestamp AS ts
ORDER BY ts DESC
LIMIT 3

You want the last 3 turns a given user had about one topic. Which part of the recall Cypher caps the result to the newest three?

Do it

  1. Start FalkorDB (Lesson 0001): docker run -d --rm --name falkordb -p 6379:6379 falkordb/falkordb:latest
  2. Index the lookup key first — this is what keeps MERGE off a full-graph scan:
    docker exec falkordb redis-cli GRAPH.QUERY agent_memory "CREATE INDEX FOR (u:User) ON (u.id)"
    Expected: Indices created: 1
  3. Write turn t-01 with the write query above (paste it as the last argument, in one pair of quotes). Expected stats: Nodes created: 4, Relationships created: 3, Properties set: 8. Re-run it — stats become Nodes created: 0 (MERGE is idempotent).
  4. Write a second turn t-02 on the same topic with a later timestamp (e.g. 1715300200, role='assistant').
  5. Run the recall query. Expected: a text, ts header, then t-02's row above t-01's, newest first. Change LIMIT 3 to LIMIT 1 and confirm only the newest turn returns.
