Lesson 0107 · The Engineer's Prompt

Verify Every Step

An agent doing ten steps that you check only at the end is an agent you cannot trust. Verify immediately after every state-changing action, because errors compound: a 5% per-step error rate becomes roughly a 40% chance of a wrong result by step ten.

By the end you can demand evidence after each agent action instead of at the end of the session, evidenced by a "verify:" line on every step and a health-check command you run after every change.

Why this matters

Your Track 02 build is a chain: write a Cypher MERGE, wire the route, read from the cockpit, record a handoff. If the MERGE in step one returns a malformed node, every later step inherits the error — the UI shows garbage, the handoff ledger points at nothing, and you discover it all at the demo. Checking only at the end means five steps to redo. Checking after each step means one.

No action is finished until a command has proven it. Attach a "verify:" line to every step of the task spec.

The idea

10xdev's seventh mistake names this the "silent killer of agent-assisted builds": "The agent does 10 steps. Step 3 did something wrong. Steps 4–10 built on top of the error. You find out at step 10 that everything since step 3 needs to be redone." The fix it prescribes is exact — "every state-changing action has a verification step immediately after. Not a big end-of-session review. A quick, specific check right after the action":

Agent writes a file → verify the file exists and has the expected content. Agent runs a migration → verify the schema matches expectations. Agent registers a component → verify it appears in the registry.

The same source gives the instruction for the prompt itself: "Add a 'verify:' line to every step in your task spec. It should be a specific, checkable assertion — not 'looks good' but 'file X exists and contains Y.'"

Why it compounds: if each step has an independent 5% chance of a silent error, the chance the whole run is clean is 0.9510 ≈ 0.60 — a 40% chance something is wrong by step ten, and you won't know where. Verify-per-step keeps every failure local, so a fix costs one step instead of the session.

This is evidence before assertions. When the agent says "done," that is a claim; the command and its raw output are the evidence. "Done" without the output is a wish — the same failure mode as an under-specified task.

# Translate each action into a check that prints proof.
# write file        -> test -f src/memory/contract.ts && grep -q recall_turns src/memory/contract.ts
# run migration     -> CALL db.labels()                       # schema claims exist
# wire endpoint     -> curl -s localhost:5173/api/recall | jq .
# wire FalkorDB     -> npm run health                          # prints the node count

Note every check returns something an eye can read: an exit code, a row, JSON. "Verify:" lines never read "looks correct."

"Add the FalkorDB read and tell me when done."

Add it, then run npm run dev and paste the exact output showing the node returned; do not say done until the command proves it.

The agent has just written the Cypher MERGE for write_turn. What does "verify every step" require right now?

Add a health-check command to your project and use it after every change.

  1. Add a script (e.g. scripts/health.ts, wired as "health" in package.json) that connects to FalkorDB and prints a count of the nodes the demo cares about — e.g. MATCH (n) RETURN count(n) AS nodes.
  2. Run it now: npm run health. Confirm it prints a number (a fresh graph may print 0), proving the connection works before you rely on it.
  3. Make it a habit: after every agent action that touches the graph, the route, or the UI, run npm run health and paste the output. Do not accept "done" without it.
  4. Add a "verify:" line to each step of your next task spec — a specific, checkable assertion, never "looks good."
