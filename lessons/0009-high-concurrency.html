High-Concurrency Reads and Writes

Many agents and users write agent memory every turn, so your graph gets hammered; these patterns keep it fast, and the win is a concurrent writer test that passes.

By the end you can fire N concurrent turn writes on one FalkorDB connection and count them back with Cypher, evidenced by the count equalling N with no duplicates and no lost turns.

← Curriculum Prev Next → Concurrency notes Cypher cheat sheet

Why this matters

High-concurrency reads and writes is a Track 02 key-focus point, and it is the one your simulated backend hides. In a multi-agent system every agent turn writes episodic memory: a new Turn appended to a Session. With several agents and users on the same graph at once, those writes arrive together, not one at a time. Your demo must survive that.

FalkorDB is built for exactly this load. Its site advertises "10K+ multi-graphs (tenants)", "linear scalability", "ultra-low latency", and a Redis-based architecture, and its published comparison chart claims P50 latency of 36 ms versus a competitor's 469 ms and ~100 MB versus ~600 MB memory (falkordb.com). Treat those as vendor claims, not the last word — the point is that the engine is designed for concurrent, multi-tenant traffic, so your job is mainly to not get in its way.

The idea

Five patterns that keep concurrent memory fast:

PatternWhy
Idempotent MERGE writesMERGE matches a pattern or creates it, so a retried or duplicated write does not create a second node. Use a separate MERGE per node — merging a whole path can duplicate an endpoint (FalkorDB MERGE docs).
One connection per processUse the official falkordb Node client and share it. The client handles concurrency over the RESP protocol; opening a fresh connection per query just adds overhead.
Write small: append a Turn, don't rewrite a SessionA new Turn is an independent write. Rewriting a whole session re-touches one node that every other writer also touches, and the cost grows with history.
Avoid a single hot nodeFunnelling every write through one hub node serializes them. Per-tenant graphs (Lesson 0008) spread load instead.
Index your lookup keysIndex node properties used in MERGE (user IDs, entity names, timestamps) so writes don't fall back to a full-graph scan (FalkorDB blog).

FalkorDB reports that its in-memory engine handles single-edge writes in sub-millisecond times, and that production deployments run dozens of agents against one store (FalkorDB blog). Be honest: no verified public benchmark exists yet for this exact high-concurrency write pattern (RESOURCES.md gap). So don't repeat a number you didn't measure — measure it yourself below.

// Write shape (one small append per turn, idempotent on Turn.id)
MERGE (s:Session {id:'load-s01'})
MERGE (t:Turn {id:$id})
  ON CREATE SET t.role='user', t.text=$text, t.timestamp=$ts
MERGE (s)-[:HAS_TURN]->(t)

Why does appending a Turn beat rewriting the whole Session for concurrent writes?

Do it

  1. Start FalkorDB (Lesson 0001) and install the official Node client (FalkorDB clients docs):

    docker run -d --rm --name falkordb -p 6379:6379 falkordb/falkordb:latest
npm install falkordb

  2. Save this as test-concurrency.mjs. It fires N writes at once on one shared connection, then counts them back:

    import { FalkorDB } from 'falkordb';

const N = 50;
const db = await FalkorDB.connect({ host: 'localhost', port: 6379 });
const graph = db.selectGraph('agent_memory');

// N writes in flight at the same time, on this single connection.
await Promise.all(
  Array.from({ length: N }, (_, i) =>
    graph.query(
      `MERGE (s:Session {id:'load-s01'})
       MERGE (t:Turn {id:$id})
         ON CREATE SET t.role='user', t.text=$text, t.timestamp=$ts
       MERGE (s)-[:HAS_TURN]->(t)`,
      { params: { id: `load-t${String(i).padStart(3, '0')}`,
                  text: `msg ${i}`, ts: 1715300000 + i } }
    )
  )
);

const res = await graph.query(
  `MATCH (:Session {id:'load-s01'})-[:HAS_TURN]->(t:Turn)
   RETURN count(t) AS turns`
);
console.log('turns =', res.data[0].turns);

await db.close();

  3. Run it:

    node test-concurrency.mjs

    Expected output:

    turns = 50

    If you see turns = 50, all N concurrent writes landed and none were lost. The MERGE on Turn.id guarantees uniqueness even if two writers raced.

  4. Prove idempotency under load: re-run the same file. The ids are deterministic, so every write matches instead of creating — the count stays 50. Then change N to 200 and re-run; expected turns = 200. That is retry-safe concurrency.

  5. Time it: wrap the write block with const t0 = Date.now() / console.log(Date.now() - t0, 'ms'). Record the number in your README as your measured result — not a quoted benchmark.

Debug tip: if the count is below N, a write rejected — add .catch(e => console.error(e)) inside the Array.from to surface it. If it is above N, you are matching the wrong session id, or a previous run used different Turn.ids. Result shape is res.data[0].turns for falkordb-ts; log res once if your version differs.
