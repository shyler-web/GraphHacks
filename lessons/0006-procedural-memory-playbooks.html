Procedural Memory: Reusable Playbooks

Store a successful tool-use pattern as a workflow subgraph, then look it up and replay it for a similar task instead of re-deriving it every time — your agent gets better with use, and you get a citable Track 02 evidence point.

By the end you can store a workflow subgraph (Workflow → Step → Tool) with MERGE and fetch its ordered steps with MATCH, evidenced by a returned, ordered step list for a given task type.

← Curriculum Prev Next → Cypher cheat sheet

Why this matters

Track 02 lists procedural memory as a required tier. It completes the three-tier memory model: episodic memory records what happened, semantic memory holds facts, and procedural memory holds how to act. FalkorDB defines it as "stored tool-use patterns and successful query strategies, represented as workflow subgraphs the agent can re-execute" (FalkorDB blog).

This is exactly what your repo already gestures at: handleApplySeniorFix and handleRunMultiAgentPrompt are fixed routines. Today, turn one of them into a "Playbook Guardrail" — a named workflow node with ordered steps — so a future similar task is a graph lookup, not a fresh guess.

The idea

A playbook is a small subgraph: one Workflow node, one Step node per action, and a Tool node per capability. Steps are Ordered by a property and chained to tools with Edge (relationship) types. Nothing here is text in a prompt — it is structure you can query.

Write it with MERGE, "the Cypher clause that matches a pattern or creates it if it does not exist, the basis of idempotent memory writes" (FalkorDB Cypher docs). Run the write twice and the graph stays the same — replay adds a successful run without duplicating nodes.

// Pattern shape
//   (:Workflow {task_type}) -[:HAS_STEP]-> (:Step {order}) -[:USES]-> (:Tool)

MERGE (w:Workflow {name: 'apply-senior-fix', task_type: 'code-fix'})
  ON CREATE SET w.summary = 'Diagnose, patch, verify'
MERGE (s1:Step {workflow: 'apply-senior-fix', order: 1})
  ON CREATE SET s1.action = 'Read the failing test'
MERGE (w)-[:HAS_STEP]->(s1)
MERGE (t1:Tool {name: 'read_file'})
MERGE (s1)-[:USES]->(t1)

RETURN w.name AS workflow, s1.order AS step, t1.name AS tool

Why is procedural memory a graph and not just a long prompt?

Do it

  1. Write the workflow below with MERGE (separate MERGE per node, per the docs' duplicate-avoidance rule). Paste into your starter query console or graph.query(...).

    MERGE (w:Workflow {name: 'apply-senior-fix', task_type: 'code-fix'})
  ON CREATE SET w.summary = 'Diagnose, patch, verify'
MERGE (s1:Step {workflow: 'apply-senior-fix', order: 1})
  ON CREATE SET s1.action = 'Read the failing test'
MERGE (s2:Step {workflow: 'apply-senior-fix', order: 2})
  ON CREATE SET s2.action = 'Apply minimal patch'
MERGE (s3:Step {workflow: 'apply-senior-fix', order: 3})
  ON CREATE SET s3.action = 'Re-run the test suite'
MERGE (t1:Tool {name: 'read_file'})
MERGE (t2:Tool {name: 'edit_file'})
MERGE (t3:Tool {name: 'run_tests'})
MERGE (w)-[:HAS_STEP]->(s1)
MERGE (w)-[:HAS_STEP]->(s2)
MERGE (w)-[:HAS_STEP]->(s3)
MERGE (s1)-[:USES]->(t1)
MERGE (s2)-[:USES]->(t2)
MERGE (s3)-[:USES]->(t3)
RETURN w.name, s1.order, s2.order, s3.order

    Expected: one row, apply-senior-fix | 1 | 2 | 3. Re-run it — the counts do not change, because MERGE is idempotent.

  2. Fetch the playbook for a task type — this is the agent's lookup before acting.

    MATCH (w:Workflow {task_type: 'code-fix'})-[:HAS_STEP]->(s:Step)-[:USES]->(t:Tool)
RETURN w.name AS workflow, s.order AS step, s.action AS action, t.name AS tool
ORDER BY step

    Expected (3 rows, ordered by step):

    workflowstepactiontool
    apply-senior-fix1Read the failing testread_file
    apply-senior-fix2Apply minimal patchedit_file
    apply-senior-fix3Re-run the test suiterun_tests

  3. Prove the lookup is keyed by task, not hard-coded. Change task_type to 'code-review' in the MATCH and re-run: zero rows. That empty result is the guardrail — no stored playbook, no automatic replay, so the agent falls back to reasoning.

  4. Wire it in: in handleApplySeniorFix, run step 2's MATCH first. If it returns rows, stream them as the plan and execute tool in step order. If it returns nothing, run the routine once, then MERGE the steps you actually used — that is how the playbook library grows. Rename the workflow to your repo's Playbook Guardrail name so the demo and the graph agree.

Debug tip: if step 2 returns nothing, check the property you filtered on. MATCH filters on exact values; a typo in task_type silently yields zero rows, not an error.
