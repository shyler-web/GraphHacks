GraphHacks · Track 02 — Reference

Graph Data Model

The proposed schema for GraphSync: one connected graph that composes episodic, semantic, and procedural memory into a three-tier memory model, plus the coordination layer that persists multi-agent state. Paste or adapt this into your README (rule 10).

← Curriculum Cypher cheat sheet Concurrency & isolation Glossary
Grounding. The three-tier split is FalkorDB's canonical agent-memory taxonomy: episodic memory is "records of past interactions, stored as timestamped event nodes linked to entity nodes"; semantic memory is "factual knowledge about the domain, the knowledge graph itself"; procedural memory is "stored tool-use patterns and successful query strategies, represented as workflow subgraphs the agent can re-execute." This model adopts that taxonomy and extends it with an explicit coordination layer (Agent, Handoff) for Track 02's shared-state and handoff requirement.

Source: Graph Database AI Agents — GraphRAG & Memory Guide, FalkorDB. See also the resource shelf.

1. Node labels

Every label below is a node with a stable id. Timestamps are Unix epoch integers (FalkorDB convention in the source guide). Colors are informational only.

TierLabelKey propertiesMeaning
Tenant:Tenant id, name, graph_key An isolation boundary. One Tenant ↔ one FalkorDB graph key. Root of the multi-graph / multi-tenant topology.
Episodic:User id, display_name The actor. Linked to past interactions so the agent can recall "what happened last time."
:Session id, started_at, ended_at, title A contiguous conversation. Groups turns and gives persistent conversation history a home.
:Turn id, timestamp, role, text, response_quality A single message/event: role ∈ {user, agent, tool}. The atomic episodic record.
Semantic:Entity id, name, type, embedding An extracted domain object (service, user, plan, dependency). Durable, independent of any one interaction.
:Fact id, statement, confidence, source_turn A durable assertion about the domain, linked to the entity it concerns and the turn it was derived from.
:Topic name A subject label that ties episodic turns and semantic entities together (e.g. auth-service-dependencies).
Procedural:Tool id, name, signature A callable capability (a Cypher query template, an API, a graph algorithm).
:Workflow id, name, trigger_domain, learned_from A reusable, re-executable sequence of steps — the stored pattern of a successful strategy.
:Step id, order, action, expected_result One action inside a workflow. Steps are chained into a subgraph the agent can replay.
Coordination:Agent id, name, role, persona_level One of the 4-agent squad (VibeArchitect L0–L1, FullStackBuilder L2–L3, SeniorAuditor L4, PrincipalResearcher L5).
:Handoff id, created_at, reason, status An event node recording transfer of state and responsibility. status ∈ {PENDING, COMPLETED, ALERT_RAISED, PLAYBOOK_ENFORCED}.
This table is the "graph data model" your README must contain. Keep the four tiers visible and name at least one property per label.

2. Relationship types

Every edge (relationship) is typed, directed, and may carry properties. Directions below are the canonical traversal direction.

TypeDirectionPropertiesMeaning
:PARTICIPATED(:User)-[:PARTICIPATED]->(:Turn)—A user took part in a turn. Opens the episodic recall path.
:IN_SESSION(:Turn)-[:IN_SESSION]->(:Session)—Groups turns into persistent conversation history.
:ABOUT(:Turn)-[:ABOUT]->(:Topic)—The turn is on-topic. The join between episodic and semantic tiers.
:MENTIONS(:Turn)-[:MENTIONS]->(:Entity)—A turn references a domain entity, feeding factual extraction.
:HAS_FACT(:Entity)-[:HAS_FACT]->(:Fact)—Binds a durable fact to the entity it describes.
:DERIVED_FROM(:Fact)-[:DERIVED_FROM]->(:Turn)—Provenance: the episodic turn this fact was extracted from (explainability).
:RELATES_TO(:Entity)-[:RELATES_TO {type}]->(:Entity)type, confidenceA typed semantic edge between two entities (depends_on, owns, etc.). This is the "each extracted relationship becomes a typed edge" rule.
:SAME_TOPIC(:Topic)-[:SAME_TOPIC]->(:Topic)—Links adjacent topics for cross-session recall.
:USES(:Workflow)-[:USES]->(:Tool)—A reusable workflow invokes a callable tool.
:NEXT_STEP(:Step)-[:NEXT_STEP {order}]->(:Step)orderChains steps into the replayable workflow subgraph.
:START(:Workflow)-[:START]->(:Step)—The entry step of a workflow.
:LEARNED_FROM(:Workflow)-[:LEARNED_FROM]->(:Handoff)—Procedural memory is written from a completed fix or audit — the "learn once" edge.
:EXECUTED(:Agent)-[:EXECUTED]->(:Workflow)atEvidence that an agent ran a workflow (for confidence weighting).
:HANDED_TO(:Agent)-[:HANDED_TO {at}]->(:Agent)atDirect edge between agents; the coordination skeleton.
:FROM_AGENT(:Handoff)-[:FROM_AGENT]->(:Agent)—Sender of a recorded handoff.
:TO_AGENT(:Handoff)-[:TO_AGENT]->(:Agent)—Receiver of a recorded handoff.
:TARGETS(:Handoff)-[:TARGETS]->(:Entity)—The semantic node the handoff concerns (the shared-state pointer).
:PRODUCED(:Agent)-[:PRODUCED]->(:Turn)—The agent authored this turn.
:MODIFIED(:Turn)-[:MODIFIED]->(:Entity)opRecords a write: which entity a turn created or changed and how.

4. Example Cypher statements

All writes use MERGE for idempotent memory writes. Indexes on the properties used in MERGE keep writes off full-graph scans (source guide, "Index strategy").

4.1 Create indexes and the tenant/user roots

CREATE INDEX FOR (u:User) ON (u.id);
CREATE INDEX FOR (t:Turn) ON (t.id);
CREATE INDEX FOR (e:Entity) ON (e.id);

MERGE (t:Tenant {id: $tenant_id})
  ON CREATE SET t.name = $tenant_name, t.graph_key = $graph_key
MERGE (u:User {id: $user_id})
  ON CREATE SET u.display_name = $display_name;

Note: FalkorDB uses one graph per tenant, so :Tenant is usually implicit in the key. Keep it if you also maintain a registry graph.

4.2 Write episodic memory (a turn) and link it to a user and topic

MERGE (u:User {id: $user_id})
MERGE (s:Session {id: $session_id})
MERGE (t:Topic {name: $topic})
CREATE (turn:Turn {
  id: $turn_id, timestamp: $ts, role: $role,
  text: $text, response_quality: $quality
})
CREATE (u)-[:PARTICIPATED]->(turn)
CREATE (turn)-[:IN_SESSION]->(s)
CREATE (turn)-[:ABOUT]->(t);

This mirrors the source guide's (:User)-[:PARTICIPATED]->(:Episode)-[:ABOUT]->(:Topic) pattern, with :Turn as the timestamped event node.

4.3 Write semantic memory (entity + fact + typed relation)

MERGE (a:Entity {id: $subj_id})  ON CREATE SET a.name = $subj_name, a.type = $subj_type
MERGE (b:Entity {id: $obj_id})   ON CREATE SET b.name = $obj_name,  b.type = $obj_type
MERGE (f:Fact {id: $fact_id})
  ON CREATE SET f.statement = $statement, f.confidence = $confidence
MERGE (a)-[:HAS_FACT]->(f)
MERGE (f)-[:DERIVED_FROM]->(:Turn {id: $source_turn})
MERGE (a)-[:RELATES_TO {type: $rel_type}]->(b);

4.4 Record a procedural workflow and an agent handoff

MERGE (w:Workflow {id: $wf_id})
  ON CREATE SET w.name = $wf_name, w.trigger_domain = $domain,
                w.learned_from = $handoff_id
MERGE (s1:Step {id: $s1_id})  SET s1.order = 1, s1.action = $a1
MERGE (s2:Step {id: $s2_id})  SET s2.order = 2, s2.action = $a2
MERGE (w)-[:START]->(s1)
MERGE (s1)-[:NEXT_STEP {order: 1}]->(s2)
MERGE (w)-[:USES]->(:Tool {id: $tool_id});

MERGE (from:Agent {id: $from_id})
MERGE (to:Agent   {id: $to_id})
CREATE (h:Handoff {
  id: $handoff_id, created_at: $ts, reason: $reason, status: 'COMPLETED'
})
CREATE (h)-[:FROM_AGENT]->(from)
CREATE (h)-[:TO_AGENT]->(to)
CREATE (from)-[:HANDED_TO {at: $ts}]->(to)
MERGE (h)-[:TARGETS]->(:Entity {id: $target_entity_id});

4.5 Recall: traverse episodic → semantic for an explainable answer

MATCH (u:User {id: $user_id})-[:PARTICIPATED]->(turn:Turn)-[:ABOUT]->(topic:Topic)
MATCH (turn)-[:MENTIONS]->(e:Entity)-[:RELATES_TO*0..2]->(related:Entity)
RETURN turn.text, turn.timestamp, topic.name, e.name, related.name
ORDER BY turn.timestamp DESC
LIMIT 20;

5. Per-tenant isolation

FalkorDB holds thousands of isolated graphs in a single instance, so each tenant gets its own memory graph without a separate deployment — the multi-graph / multi-tenant topology. Select the graph by key; never mix tenant data in one graph.

graph = db.select_graph(f"tenant:{tenant_id}")   # one graph per tenant
graph.query("MERGE (u:User {id: $id})", {"id": user_id})

Because every write is scoped to a graph key, an agent can only reach the current tenant's nodes; cross-tenant reads require an explicit second select_graph. This is what makes "separate memory per user or tenant" a structural property rather than a query filter. For concurrent writers, batching, and lock patterns across these graphs, see Concurrency & isolation notes.
