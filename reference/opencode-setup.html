opencode reads config once at startup. Restart opencode after editing any config file, agent, or skill — otherwise your change is invisible to the running session.

1 · AGENTS.md — what opencode auto-reads

AGENTS.md is the project's ambient rule file. opencode loads it into every session's context automatically (traced from the current directory up to the git worktree). This project keeps it deliberately small because it is injected into every session. The build order, schema, and per-task plan live in the curriculum and reference/insight.html §4 instead — keeping the context budget lean.

Auto-read filePurpose
AGENTS.mdLocked context, rules, stack, commands, security. Always in context.
docs/decisions.mdDecision records D1–D5 (loaded via the instructions array, below).
PROGRESS.mdLiving status + recent commits (loaded via instructions).
The ALWAYS block (AGENTS.md §"ALWAYS — locked context") is the four facts a session must never re-derive: (1) the binding rules — FalkorDB is the load-bearing graph (rule 3), Track 02, deadline Oct 18; (2) goal + exit criterion — stopping FalkorDB visibly breaks the app; (3) the locked reversible/expensive decisions (D1–D5); (4) the health check npm run health = MATCH (n) RETURN count(n). Edit it by appending a numbered fact and, if it reverses a locked decision, recording that decision in docs/decisions.md first — do not reopen a locked decision silently.

To edit: change AGENTS.md, then restart opencode. Add durable cross-session facts only — task-specific asks belong in a spec card, not the rule file. A new file added to the instructions array in opencode.json is also auto-read.

2 · Subagents

Defined as markdown in .opencode/agent/ (front-matter description, mode: subagent, temperature, permission). Invoke with @name, or let a primary agent call them via the Task tool. Permissions below are quoted from each file's front-matter.

AgentPurposePermissionsWhen to use
researcher External facts, APIs, docs (web + DeepWiki), cited. edit deny · bash deny · webfetch allow · websearch allow Current, citable info on FalkorDB, LangSmith, MCP, Tavily, memory patterns.
teacher Authors one-win HTML lessons and reference pages. edit allow · bash ask · webfetch allow Creating or revising files under lessons/ or reference/.
planner Turns vague goals into spec cards and decision records — no product code. edit allow · bash deny · webfetch allow Scoping a task, choosing between options, "let's build X".
builder Implements a spec card against the project; stops at first blocker. edit allow · bash allow · webfetch allow Doing the build work of a vertical slice.
reviewer Reviews for correctness, rule-3 "real work", regressions — read-only. edit deny · bash ask · webfetch allow Before committing, or when a change claims to be "done".
debugger Diagnoses a failure with the scientific method before any fix. edit ask · bash allow Something breaks, hangs, or behaves unexpectedly.
gitter Verifies, then commits + pushes with decision-bearing messages. edit deny · bash: *: ask, git * / npm * / graphify *: allow, cat .env*: deny After a milestone passes its exit criterion.
graphify-keeper Rebuilds and queries the graphify knowledge graph. edit allow · bash: *: ask, graphify *: allow, cat graphify-out/*: allow After significant changes, or to answer a codebase question.

3 · Skills

Each skill is a folder with a SKILL.md under .opencode/skills/ (discovered via skills.paths, see §4). opencode lists them in the skill tool description; an agent loads the full text on demand. They fire by description.

SkillWhat it enforcesFires when
prompt-playbook The 5-line spec card: what it builds · exit criterion · out of scope · locked decisions · verify step. Before handing any build/fix/change task to the AI; on "prompt", "spec", "task".
verify-change The per-change loop: run the exit criterion immediately, never batch; this project's checks (npm run build, npm run health, nc -z localhost 6379, rule-3 flip). After writing code, wiring data, or before committing.
track02-build Locked stack, build order T0–T4, the five key-focus points, rules 3/10/11/12. When starting or resuming build work or checking what to do next.

Instructions

instructions is an array of paths/globs added on top of AGENTS.md. Here it loads docs/decisions.md and PROGRESS.md every session. Add a durable rule source here rather than bloating AGENTS.md.

Permissions — git allowed, .env denied

Permission values are allow / ask / deny; with glob maps the last matching rule wins. This project:

KeyRuleEffect
edit*allow
edit**/.env, **/.env.*, **/*.pem, **/*.keydeny — secrets never edited
bash*ask
bashgit *, npm *, npx *, docker *, graphify *, ls *allow
bashcat .env*, cat **/.env*deny — secrets never printed
bashrm -rf *ask

MCP servers

Two local MCP servers, both enabled: true. Environment values use {env:VAR} substitution — the secret never appears in the JSON. Fill the variables in .env (copied from .env.example).

.env.example declares the full variable set: FALKORDB_HOST, FALKORDB_PORT (the load-bearing graph); GEMINI_API_KEY (LLM); TAVILY_API_KEY (tool); LANGSMITH_TRACING, LANGSMITH_API_KEY, LANGSMITH_PROJECT (observability). Only .env.example is committed.

5 · The graphify loop — query before exploring

Treat the graphify graph database as durable, model-agnostic agent memory for the codebase itself. Query before reading files: graphify query "<question>" (broad), graphify path "<A>" "<B>" (shortest path), graphify explain "<Node>". After significant changes, refresh it: graphify update . (incremental). Rail-map: graphify-out/GRAPH_REPORT.md; interactive view: graphify-out/graph.html.

Why it is cross-model memory: the graph persists in the repo, not in a chat session, so a brand-new session on any model rebuilds context from it instead of re-reading the whole repo. This is the same reason the context budget matters — the graphify-keeper subagent owns keeping it current and honest (no invented edges). Rebuild it in the same commit as the change it describes.

6 · Restart after editing config

Config is loaded at startup. opencode.json, the agent markdown files, and SKILL.md files are read when opencode launches. After editing any of them, restart opencode so the running session picks up the change. Editing AGENTS.md or another instructions file also requires a restart to re-inject context.
