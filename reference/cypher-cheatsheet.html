Clauses at a glance

ClauseOne-line purpose
MATCHFind existing patterns (nodes + edges); no match → no row.
OPTIONAL MATCHLike a LEFT JOIN — unmatched elements come back null instead of dropping the row.
WHEREFilter rows by predicates (comparison, string, IN, boolean logic, pattern predicates).
CREATEAlways create new nodes/edges — never checks for duplicates.
MERGEMatch the pattern or create it — the basis of idempotent memory writes.
SETCreate or update properties (and labels) on bound entities.
DELETERemove nodes/edges; deleting a node also deletes its edges.
DETACH DELETEDelete nodes and their edges explicitly; in FalkorDB same behavior as DELETE.
RETURNProject the result set; non-aggregated expressions become grouping keys.
WITHPipe results between query parts and control which variables stay in scope.
ORDER BYSort output (ASC/DESC), possibly by several keys.
LIMITCap the number of returned rows (does not stop eager writes — see gotchas).
UNWINDExpand a list into one row per element — bulk writes and batch reads.

Pattern syntax legend

PatternMeaning
()Anonymous node.
(a)Node bound to variable a.
(a:Label)Variable with a label.
(:Label {key: 'value'})Label plus an inline property filter (equivalent to WHERE).
(a)-[]->(b)Any directed edge from a to b.
(a)-[r:TYPE]->(b)Typed, directed edge (relationship) bound to r.
(a)-[:TYPE]-(b)Typed edge, either direction.
(a)-[:KNOWS*]->(b)Variable-length path, 1 to infinity hops.
(a)-[:KNOWS*2]->(b)Exactly 2 hops.
(a)-[:KNOWS*1..3]->(b)Between 1 and 3 hops.
(a)-[:KNOWS*..3]->(b)Up to 3 hops (lower bound defaults to 1, upper to infinity).
p = (a)-[:KNOWS*1..3]->(b)Named path; inspect with nodes(p), relationships(p), length(p).

Agent-memory snippets

1 · Upsert a memory with MERGE

Merge one entity per clause. A single MERGE over a whole path either matches all of it or creates all of it, duplicating existing endpoints when only the edge is missing.

MERGE (u:User {id: $userId})
MERGE (m:Memory {id: $memoryId})
  ON CREATE SET m.text = $text, m.created = timestamp(),
                m.kind = 'episodic'
  ON MATCH  SET m.text = $text, m.last_seen = timestamp()
MERGE (u)-[:REMEMBERS]->(m)

This is the idempotent write pattern behind episodic memory and semantic memory alike: re-running it never forks a duplicate node.

2 · Recall the last N turns for a user

The conversation history is one timestamped node per turn, chained so ordering survives a reload.

MATCH (u:User {id: $userId})-[:SAID]->(t:Turn)
RETURN t.role AS role, t.text AS text, t.at AS at
ORDER BY t.at DESC
LIMIT $n

Re-insert in reverse client-side to restore chronology. LIMIT caps the read — safe here because this query has no eager write (see gotchas).

3 · Find all facts about an entity

Semantic memory is durable facts as entity nodes joined by typed edges. This walks every outgoing fact from one entity.

MATCH (e:Entity {name: $name})-[r]->(o)
RETURN type(r) AS predicate, o.name AS object, o.value AS value
ORDER BY predicate, object

For a symmetric lookup, match -[r]- (undirected) and read startNode(r) / endNode(r) when you need the direction back.

4 · Fetch a workflow's ordered steps

Procedural memory is a reusable workflow subgraph — steps hanging off a workflow node, each carrying its own order.

MATCH (w:Workflow {id: $workflowId})-[:HAS_STEP]->(s:Step)
RETURN s.order AS step, s.tool AS tool, s.input AS input
ORDER BY s.order ASC

To replay a handoff chain, traverse the workflow edges in order rather than reading steps as loose rows:

MATCH p = (w:Workflow {id: $workflowId})-[:NEXT*1..10]->(s:Step)
RETURN nodes(p) AS path, length(p) AS hops

Gotchas that bite

CREATE vs MERGE

CREATE (m:Memory {id: $id}) on every turn silently multiplies nodes. Use MERGE for anything that must be idempotent; use CREATE only for genuinely new entities (a fresh turn, a new event). And remember: merging a whole path can duplicate endpoints — merge each entity in its own clause, then merge the edge.

DETACH DELETE

Deleting a node always deletes its incoming and outgoing edges. FalkorDB never leaves orphaned edges, and its DELETE already behaves like DETACH DELETE — both keywords work the same way. Wipe a graph with MATCH (n) DETACH DELETE n.

Case sensitivity

Labels, edge types, and property keys are matched exactly as written — :User is not :user, and m.startedAt is not m.started_at. Pick one casing per key and use it everywhere (including in your React/TS client code). Clause keywords are conventionally uppercase; keep labels and properties case-consistent or MATCH returns nothing.

Returning whole paths

Returning a bound node or path returns the entity, not its properties: RETURN u returns the full node. Project the fields you need instead. When a relationship in a pattern is never referenced elsewhere, FalkorDB only verifies that at least one match exists — reference the alias (e.g. RETURN count(b), e) when you must count every match. Named paths expose their parts: nodes(p), relationships(p), length(p).

LIMIT does not restrict eager writes

UNWIND [1,2,3] AS v CREATE (a {property: v}) RETURN a LIMIT 1 creates three nodes and returns one. LIMIT applies after CREATE, SET, DELETE, MERGE, and aggregating projections. Filter before you write, not after.

No GROUP BY, no regex operator

Non-aggregated expressions in RETURN are implicit grouping keys. Regex operators are unsupported — use STARTS WITH, ENDS WITH, CONTAINS, or string.matchRegEx().

Track 02 tie-in. A multi-graph / multi-tenant topology gives each user or tenant a separate memory graph, so the same Cypher runs per tenant with no tenantId filter needed. Every memory write that matters should be a MERGE, so concurrent agents can retry without corrupting the graph.
