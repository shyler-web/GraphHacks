1 · Key-focus points → the evidence that proves each one

Track 02’s key focus, quoted from the hackathon page: “Episodic, semantic, and procedural memory · Persistent conversation history · Shared state and handoffs between agents · High-concurrency reads and writes · Separate memory per user or tenant.” [event page]

Key-focus point What it means (per the Glossary) Concrete evidence to show
Episodic memory A record of specific past interactions, stored as timestamped event nodes linked to the entities involved, so an agent can recall “what happened last time.” Query the graph for a past session’s events and screenshot the returned event nodes with timestamps. Show the Cypher that created them (MERGE-based write, idempotent).
Semantic memory Durable factual knowledge about the domain — entities, attributes, and their relationships — independent of any single interaction. Show a fact extracted from a message becoming connected entity nodes and edges in one query. Screenshot a traversal that answers a question from the fact graph, not from loose text.
Procedural memory Stored tool-use patterns and successful query strategies, represented as reusable workflow subgraphs an agent can re-execute. Replay a workflow subgraph in the demo: run a stored tool-use pattern once, show it stored, then re-execute it on a new input. Screenshot the subgraph in FalkorDB Browser.
Persistent conversation history Agent memory: the persistent, queryable state an agent reads and writes across sessions so it does not start from zero each time. End a session, restart the app, ask a follow-up that depends on the earlier turn, and screenshot the recalled history. Restart must not clear the graph (real FalkorDB, not in-process state).
Shared state and handoffs between agents Handoff: the transfer of state and responsibility from one agent to another, recorded in the graph so the receiving agent knows what was done and why. Run a two-agent flow where agent B reads agent A’s recorded state. Screenshot the handoff ledger — the node/edge recording who handed off, what and why — and the query agent B ran to read it.
High-concurrency reads and writes Many agents reading and writing agent memory at once without losing or corrupting state; writes stay idempotent via MERGE. Run a concurrent writer test (many parallel writes via one client), then query the count and assert no duplicates / no lost writes. Screenshot the test output and the reconciled graph state.
Separate memory per user or tenant Multi-graph / multi-tenant topology: FalkorDB’s ability to hold thousands of isolated graphs in one instance, so each user or tenant gets a separate memory graph without a separate deployment. Show two named graphs in one FalkorDB instance. Query user A’s graph and user B’s graph and screenshot that neither sees the other’s nodes. State the graph-name → tenant mapping.
Judging note. The event’s own “work the graph has to do” list — follow connections, remember across sessions, share state between agents, connect people/projects/decisions, show the path behind an answer — is the framing judges use. Every row above should be visible in the video, not just in the repo. [event page]

3 · The “real work” test (rule 3)

Rule 3, quoted: “The graph has to do real work. A visualisation drawn on top of ordinary storage does not qualify: if the product still works once FalkorDB is taken out, the graph is decoration rather than the thing the product runs on.” [rules, rule 3]

If FalkorDB were removed, would the product still work?

Pass condition: with FalkorDB stopped, the product fails — memory recall, handoffs, and isolation all return nothing, because the graph is where agent memory lives. If it keeps working from a cache or a JSON file, the graph is decoration. Say this out loud in the video: point at the running FalkorDB instance and state that removing it breaks the demo.

4 · Two-minute demo shot list

  1. 0:00–0:15 — Frame it. One sentence: a multi-agent system whose memory is a real FalkorDB graph. Show the FalkorDB container/browser running.
  2. 0:15–0:35 — Three-tier memory. Write one turn, show episodic, semantic, and procedural memory landing in the graph as nodes and edges. Open FalkorDB Browser on the data model.
  3. 0:35–0:55 — Persistence. Restart the app; ask a follow-up that depends on the earlier session; the answer recalls the stored history.
  4. 0:55–1:15 — Handoff. Agent A finishes work; agent B reads A’s recorded handoff and continues. Screenshot the handoff ledger.
  5. 1:15–1:35 — Concurrency. Fire the parallel-writer test; show the output and the deduplicated graph state (idempotent MERGE writes).
  6. 1:35–1:50 — Isolation. Switch tenant; show the second graph sees none of the first tenant’s nodes.
  7. 1:50–2:00 — Real work + close. Say the rule-3 line: remove FalkorDB and the product breaks. Point to repo, README, queries, and the track name.
Every key-focus point ticked, all six rule-10 items ticked, the rule-3 line said on camera, and a two-minute video that shows all five memory behaviours in the running system.
