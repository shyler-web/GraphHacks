1. Why agent memory is write-heavy, and why FalkorDB

Agent memory is the persistent, queryable state an agent reads and writes across sessions. In a coordination demo, every agent step both reads context and appends a result — an Episodic memory Node (the turn), often a Semantic memory update, and a Handoff. That read-modify-write loop runs once per step per agent, so the workload skews hard toward small writes with a traversal on every read.

A Graph database stores data as Nodes and Edges (relationships) and traverses them directly. Because recall is a traversal rather than a join, the per-step read cost stays tied to the three-tier memory model fan-out you actually touch, and the whole thing can be expressed in Cypher. FalkorDB advertises itself as an "ultra-fast, multi-tenant Graph Database", is "Redis-based", and claims linear scalability. Its homepage comparison table reports single-digit-millisecond read latency (P50 36 ms, P95 74 ms, P99 83 ms in their chart) and roughly 100 MB vs 600 MB memory against a competitor.

Be honest about the numbers. Those figures are FalkorDB's own vendor comparison chart on falkordb.com, not a measurement of a concurrent-writer workload for an agent-memory workload. RESOURCES.md flags this as a Gap: no verified benchmark data on high-concurrency write patterns for this exact use case. Treat the vendor numbers as a starting point and produce your own numbers (section 7) to defend the design.

2. Idempotent writes: MERGE instead of CREATE

MERGE "matches a pattern or creates it if it does not exist." That is the basis of an idempotent write: if the same Turn or fact is written twice — a retry, a duplicate event — CREATE makes a second Node, while MERGE binds to the existing one. Prefer MERGE for every entity you key by a natural identity (turn id, user id, tool name).

WriteClauseRetry behavior
New fact / entityMERGE (f:Fact {id:$id})Idempotent — re-run is a no-op
New turnMERGE (t:Turn {id:$turnId})Idempotent on the turn id
Edge between known nodesMERGE (a)-[:NEXT]->(b)Safe when a and b are already MATCHed
Guaranteed-unique eventCREATENot retry-safe — duplicates
// Retry-safe turn append: bind the session, then MERGE the turn, then the edge.
MATCH (s:Session {id: $sessionId})
MERGE (t:Turn {id: $turnId})
  ON CREATE SET t.role = $role, t.text = $text, t.ts = $ts
MERGE (s)-[:HAS_TURN]->(t)
RETURN t;

Two rules from the docs: merge each entity with its own MERGE rather than a full path, and use ON CREATE SET / ON MATCH SET to set properties conditionally. Merging a whole path (MERGE (a)-[:R]->(b) with new endpoints) can silently create duplicate Nodes, because a partial match fails and the entire path is created.

3. Append-over-rewrite

Never rewrite a whole session Node on each turn. A fat SET s.history = [...] makes every writer touch the same row-like hotspot and grows the write size linearly with session length. Append a small Turn node and link it instead — writes stay O(1) in size and stay independent per turn.

PatternPer-turn writeEffect
Rewrite session blobRe-serialize whole sessionContention on one node; write size grows with length
Append Turn node + edgeOne small node, one edgeConstant-size write; turns never conflict
Append Episodic + update a counterSmall node; SET on shared nodeCounter is a hotspot — see section 6

4. One graph per tenant (multi-graph topology)

Multi-graph / multi-tenant topology is FalkorDB's ability to hold thousands of isolated graphs in one instance, so each user or tenant gets a separate memory graph without a separate deployment. FalkorDB states it "natively supports multi-tenant and multigraph environments with zero overhead" and that each tenant's graph "operates in full isolation" for data security and privacy. The homepage advertises "10K+ multi-graphs (tenants)".

The client selects the graph by name — no per-tenant server, no schema prefix. The graph is created automatically on first query; there is no CREATE GRAPH command.

ClientSelect a graphNotes
Python (falkordb-py)g = fdb.select_graph('tenant1_graph')g.query(...) runs isolated
Node/TS (falkordb-ts)const g = fdb.selectGraph('tenant1_graph')Created on first write
Raw protocolGRAPH.QUERY <graphKey> "..."Graph key is the first argument
# Python — one client, many isolated memory graphs
fdb = FalkorDB(host="localhost", port=6379,
               username="falkordb", password="your-password")
tenant_graph = fdb.select_graph(f"tenant_{tenant_id}")
tenant_graph.query("MATCH (t:Turn) RETURN t ORDER BY t.ts DESC LIMIT 20")
Isolation is a correctness boundary. A tenant graph is the unit of isolation. Do not carry a tenant_id property into a shared graph as your only isolation and call it multi-tenancy — use the topology so a query cannot cross tenants even if a predicate is forgotten. FalkorDB Cloud adds per-tenant "own data, queries, and access controls".

5. Connection usage

Create the client connection once and share it; open per-request connections only if you deliberately want a fresh session. The official clients (Python, Node.js, Java, Rust, Go, PHP, C#) are the supported path; FalkorDB speaks the Redis protocol and also supports Bolt. Because FalkorDB runs queries through a server-side thread pool, concurrency is bounded by the server, not by how many sockets you open.

6. Hot-node avoidance

A single Session or User Node that every writer updates is a serialization point: all concurrent turns queue behind that one key. Keep the fan-in node read-mostly, and push the volatile part out to appended nodes.

Anti-patternWhy it serialisesFix
Every turn SET session.turn_countAll writers mutate one nodeAppend Turn nodes; derive count with count() at read time
One shared User node holding latest stateLast-write-wins; contentionAppend state-change nodes; keep User mostly static
Global handoff counterFan-in on one node per handoffPer-agent counters or no counter

Design read as MATCH (s:Session {id:$id})-[:HAS_TURN]->(t:Turn) RETURN t ORDER BY t.ts — traversal over appended nodes instead of a mutable blob. This keeps writers independent, so server-side thread-pool concurrency (THREAD_COUNT) can actually be used across writers.
