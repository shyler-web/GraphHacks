Git Workflow

The commit history is the next session's memory: what changed, the decision and why, and the evidence. This is the command sheet for committing each verified unit and pushing it to the public remote (rule 10) without ever leaking a secret.

Command cheat

CommandWhat it does
git statusShow the working tree and which changes are staged; your read-before-you-act check.
git add <path> / git add -AStage a path, or every tracked + untracked change, for the next commit.
git diff --cachedShow the staged diff — exactly what will go into the next commit (the pre-commit secret check).
git commit -m "<message>"Record the staged snapshot with a message that briefs the next session.
git remote add origin <url>Name your GitHub repo origin so push/pull can reach it.
git push -u origin mainPush main and set origin/main as its upstream (first push only).
git pushPush the current branch to its already-configured remote (every verified commit after the first).
git log --oneline -10The last ten commits, one line each — what happened recently.
git log --grep="decision" -5Search commit messages for a term — recover what was decided and why.

The commit-message template

10xdev.blog names the failure directly: the agent "doesn't" remember what it decided across sessions; without a durable record it "will re-derive the decision, sometimes arriving at a different answer." The fix is not sticky notes — it is the git history written as a briefing (lesson 0110). Use this shape:

<type>(<area>): <what changed>; decision: <the decision> (<why>); verify: <evidence>

Keep the word decision in it so git log --grep="decision" finds it. Two real examples from this project:

feat(memory): persist Turns to FalkorDB via MERGE; decision: one graph per tenant (D2); verify: npm run health = 2
chore(repo): initialise git repo + first commit; decision: public repo is the source of truth (rule 10); verify: git log --oneline shows 1 commit

Each message answers the three questions a cold session asks: what changed, which decision (and why), what evidence proved it. A commit that says only wip forces the next session to re-read the diff and re-derive the reasoning.

Pre-commit secret check

Before every commit, look at the staged diff and confirm no secret is in it (AGENTS.md security rule):

git diff --cached

Scan the output for: a filename .env/.env.* (other than .env.example); anything that looks like a key or token value; a real value where .env.example has an empty slot (GEMINI_API_KEY=, TAVILY_API_KEY=, LANGSMITH_API_KEY=); *.pem or *.key. If you find one, unstage it with git restore --staged <path>, fix .gitignore or the file, and re-check. If a secret was already committed, rotate it — removing it later does not un-leak it.

Work in small, verified units. After a unit passes its exit criterion, commit immediately — do not batch. Push after every verified commit so the public repo stays the source of truth. Never force-push; never commit broken code as "done." If it is not verified, it is not done.

The rhythm

  1. Verify — the unit passes its exit criterion (run npm run health after anything touching data).
  2. Inspect — git status, then git diff --cached after staging; confirm no secret is staged.
  3. Commit — git add -A then git commit -m "<template>", one verified unit per commit.
  4. Push — git push immediately after the verified commit.

Creating the GitHub remote

The repo is already initialised locally with a first commit. Create an empty public repository on GitHub, then connect and push it. Per the GitHub quickstart, create the repo in the browser (New repository → name → visibility Public → do not add a README, since you already have commits), then:

git remote add origin https://github.com/<you>/GraphHacks.git
git branch -M main
git push -u origin main

git push -u origin main pushes main and records origin/main as its upstream, so every later push is just git push. (GitHub's own quickstart uses git push --set-upstream origin HEAD, which does the same for the current branch.) If you add a README on GitHub instead, pull first — git pull --rebase origin main — before pushing so the histories are not unrelated.

Once pushed, the public repo is the submission artifact (rule 10): a reviewer clones it, reads the history with git log, and can trace every reversible decision and its evidence without asking you.
