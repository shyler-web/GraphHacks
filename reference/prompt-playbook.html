The Engineer's Prompt Playbook

The compressed capstone of The Engineer's Prompt course. One page you keep open: the build loop, the spec-card, the context budget, the debugging loop, the decision rubric, the autonomy tiers, and the weak→senior prompt library. Every claim cites a primary source. Print it and pin it.

The one idea. Prompting is the wrong lever. What you control is context — what the model has access to when it runs — and the research behind this page says context engineering beats prompt phrasing by a wide margin (teams that build context pipelines see 20–45% faster cycles). [10xdev.blog] This playbook is mostly a context-control manual wearing a prompting costume.

1 · The Build Loop

Every task — a FalkorDB write pattern, a React component, a README — moves through the same six gates. One line each. Skipping a gate is how you spend a whole hackathon hour rebuilding something.

GateWhat it meansExit when…
1 · PlanSay what you want in one sentence and what "done" verifiably looks like.You can state the exit criterion without hedging.
2 · SpecWrite the 5-line spec card (§2). Three minutes that saves hours.All five lines are filled; the check is a specific assertion.
3 · ContextLoad the ALWAYS bucket and only the task's ON-DEMAND files (§3).The agent has the goal, the constraints, and the touching code — nothing else.
4 · BuildThe agent executes the spec inside its autonomy tier (§6).The build completes or the agent stops and reports a blocker (§4).
5 · VerifyRun the spec's check immediately — not at the end of the session.The assertion passes, with output you can point at.
6 · CommitCommit with a message that carries the decision and the why.git log alone briefs the next session's agent. [10xdev.blog]
Never let the agent build on an unverified step. Bug at step 3 plus steps 4–10 on top = redo all ten; verify per action and it is a one-step fix. [10xdev.blog]

2 · Spec-Card Template

An under-specified task is a wish, not a task: the agent either stops at the first ambiguity, invents requirements, or does something technically correct and wrong for your context. The fix is a mini-spec before every agent task. Teams using spec-driven tasks report 3–10× higher first-pass success. [10xdev.blog]

The five lines — copy them verbatim:

1. What it builds      — one sentence.
2. Exit criterion      — a specific, verifiable check (not "it works").
3. Scope boundary      — what is explicitly NOT being built.
4. Locked decisions    — what the agent may not reopen.
5. Verification step   — the exact command/assertion that proves done.

Worked example A — a code task (Track 02)

Spec card · episodic turn write

1. What it builds    Persist one conversation turn as an episodic Turn node
                     linked to its User in FalkorDB, idempotently.
2. Exit criterion    Running the write twice for the same turnId leaves
                     exactly ONE Turn node, count == 1.
3. Scope boundary    No semantic extraction, no UI. Write path only.
4. Locked decisions  MERGE per entity (never CREATE for turns); property
                     keys are camelCase (turnId, role, text, at).
5. Verification step `MATCH (t:Turn {turnId:$id}) RETURN count(t)` returns 1
                     after two calls. Paste the output.

Worked example B — a research task

Spec card · handoff pattern research

1. What it builds    A short, sourced answer: does a standard shared multi-agent
                     handoff pattern exist over FalkorDB? (Yes/no + evidence.)
2. Exit criterion    ≥3 sources consulted; each claim has a URL; an explicit
                     "no trusted source found" line if none exists.
3. Scope boundary    Coordination/handoff only — NOT general agent memory.
4. Locked decisions  Prefer primary/docs sources over blog summaries; no
                     parametric guesses dressed as findings.
5. Verification step Quotes + links returned; I can open each one.
Take your next FalkorDB task — wiring the cockpit to the real graph — and write its spec card before you type a prompt. If line 2 is not a runnable check, rewrite it until it is.

3 · Context Budget

Too little context and the agent hallucinates; too much and it loses focus and pulls details from the wrong file. Control the budget with three buckets. [10xdev.blog]

BucketContentsWhen
ALWAYSProject structure & layer rules · current phase goal + exit criteria · locked decisions the agent cannot reopen · current health status.Injected at session start, every session.
ON DEMANDRelevant function contracts · adjacent code the task touches · open issues for this area · the specific Cypher/queries in play.Loaded per task, only what that task needs.
NEVERThe entire codebase · resolved issues from past phases · completed phase specs · the whole chat history.Never dumped wholesale.
Brief the agent like a good manager: the goal, the constraints, the relevant background — not a 200-page document that says "figure it out." [10xdev.blog]

4 · The Debugging Loop

Guess-and-check has three baked-in failure modes: tunnel vision (you chase the first plausible cause), fixing before reproducing (symptom moves, you declare victory), and no memory (each attempt overwrites the last). A method attacks all three. [maxtdesign]

  1. Reproduce before you theorize. Write down expected, observed, and the minimal reliable repro. No confirmed repro, no fix — the most common AI-debugging failure is a confident patch for a bug nobody reproduced. Tell the agent: do not propose a fix until the repro is confirmed. [maxtdesign]
  2. Force three ranked hypotheses. Even when one feels obvious — the second and third are where the bug usually hides. Each gets a claim, a test, and a prediction written before you run it. Rank by likelihood × ease of testing, not likelihood alone. [maxtdesign]
  3. Run the cheapest discriminating test. Confirm → root cause. Falsify → log it, re-rank with the new constraint; a falsified test told you where the bug is not. [maxtdesign]
  4. Fix the root cause — minimum change. Resist refactoring the neighborhood. Write the regression test that would have failed before the fix, in the same commit. If it is genuinely untestable (a real race, a UI glitch), say so and write a manual check instead of a test that asserts nothing. [maxtdesign]
"It worked yesterday" shortcut — git bisect. When a bug is new, stop rereading the diff. Find a good commit and a bad commit, then binary-search between them with one deterministic test command; git walks you to the exact introducing commit in a handful of steps. Your first hypothesis becomes "something in this one commit," which is very cheap to test. [maxtdesign]
When you are four rounds in and every test falsified, that is not "try harder" — it is a sign your mental model is wrong. Have a fresh reviewer explain the suspect code cold, without your hypotheses. Solo, ask the AI to explain what the code does with no bug context, then compare. [maxtdesign]

5 · Decision Rubric

Seniors ask "how does this system behave?" before "does this component work?" — boundaries, feedback loops, emergence, and resilience are where the failures hide. [Serban] Run a decision through these questions:

QuestionIf yes…If no…
Is it mandatory?It is not a choice — just build it to spec.It is a tradeoff; weigh the rest.
Reversible or irreversible?Reversible → decide fast, cheap to undo, verify and move.Irreversible (schema, tenant model, public API) → decide deliberately. Draw the system first. [Serban]
What evidence decides it?If a cheap test/measurement exists, run it and let evidence decide.If not, you are guessing — say so and pick the option with the smaller blast radius.
Cost-of-change & decomposabilitySmall, independently shippable change → build now in a bounded sprint.Large or entangled → split it; if the pieces share one bottleneck, that coupling is the real decision. [Serban]
Failure-mode analysis is the reflex: for any design, cycle "what happens when X fails?" through every dependency — FalkorDB down, stale read, malformed data, rate limit hit, tenant graph missing. It forces you to see the system in an uncertain environment, not an idealized test. [Serban]

6 · Autonomy Tiers

Treating a novel architecture decision and a mechanical rename the same way is inefficient in both directions. Decide the tier before the task and write it at the top of the spec. [10xdev.blog]

TierModeUse when
Tier 1 — InteractiveYou watch every step; the agent proposes, you approve.Novel decisions, architecture, anything where the wrong choice is expensive. New to a concept (graph modelling).
Tier 2 — Bounded sprintThe agent works independently for 30–60 min and reports at a checkpoint.Implementing a spec you already wrote: wiring the cockpit, writing Cypher, tests, a refactor.
Tier 3 — Unattended batchThe agent runs unattended; you review results.Purely mechanical: formatting, docs, dependency updates, generated boilerplate.

Structure the session around three roles, not one. One agent for everything accumulates half-remembered context, blurs its role, and starts touching layers it should not. [10xdev.blog]

RoleOwnsHard rule
BuilderThe app layer — follows the spec, produces the feature.Stops at the first blocker and writes an exact issue report; never improvises around it.
FixerThe core/lower layer the builder depends on.Reads blocker reports, fixes root cause, never edits the app being built.
ReviewerIndependent verification.Explains code cold and checks the exit criterion; not the author's context.
Separating builder from fixer is not just tidiness: the builder meets bugs the way a real user does and cannot rationalise them away, which produces precise, actionable reports. [10xdev.blog]

7 · Weak → Senior Prompt Library

Eight swaps. The right column is not longer for its own sake — it carries the spec card, the context bucket, the boundaries, and the verify line. Use them as templates, not scripts.

"Add agent memory to the app."

"Add episodic memory: persist each conversation turn as a :Turn node linked to its :User via MERGE (camelCase keys). Exit criterion: two writes of the same turnId leave count(t)==1. Out of scope: semantic extraction, UI. Verify: paste the MATCH … RETURN count(t) output. Don't reopen the three-tier model."

"Fix this bug."

"Expected: MERGE dedupes turns. Observed: duplicate :Turn nodes after retry (stack/log line below). Repro: run the writer twice with the same turnId. Do not propose a fix until the repro is confirmed. Then give 3 ranked hypotheses with claim/test/prediction and run the cheapest test first."

"It doesn't work."

"The recall query returns null for a user with saved turns. Expected: last 5 turns ordered by at DESC. Observed: empty result (exact query output pasted). Repro: seed one turn, run the read. Here is the ALWAYS context (schema + locked keys) and the ON-DEMAND query file — tell me what is missing before guessing."

"Make it better."

"Improve recall latency only. Exit criterion: read of last 20 turns p95 under 50ms on the local graph. Boundary: do not change the write path or the schema. Locked: MERGE-per-entity stays. Verify: before/after timing on the same seed data. If you can't measure it, say so instead of optimising blind."

"Explain this."

"Explain what this Cypher does line by line, then the graph shape it touches. Audience: I'm new to Cypher. Constraint: no jargon I haven't met; define MERGE and variable-length paths if you use them. End with one sentence on what would break if the edge direction were reversed."

"Review this."

"Review this handler against our locked decisions (idempotent writes, camelCase keys, per-tenant graph). Report only: correctness bugs, boundary violations, and missing failure handling when FalkorDB is down. For each, cite the line and the rule it breaks. No style nits. State confidence per finding."

"Research X."

"Research whether a standard shared multi-agent handoff pattern exists over FalkorDB. Consult ≥3 sources, prefer primary docs over summaries; give a URL per claim. Explicitly write 'no trusted source found' rather than guessing. End with: does this change our handoff-ledger design? Cite each source inline."

"Refactor this."

"Refactor the write path into one reusable function. Exit criterion: existing tests still pass, and the function is called from both the cockpit and the batch seeder. Boundary: no behaviour change, no schema change. Locked: idempotent MERGE semantics. Verify: run the test suite and paste the summary. Show the diff before applying."

Pick the three prompts you sent most this week. Rewrite each into the senior column with a spec card, a boundary, and a verify line. Keep them in a prompts.md in the repo as reusable assets.

8 · Question Templates

Bug report (paste this when something fails)

Expected:   the precise behaviour I wanted.
Observed:   the exact error / wrong value / log line (not "it crashes").
Repro:      the minimal sequence that triggers it, reliably.
Tried:      what I already changed and what happened.
Ask:        do not fix until the repro is confirmed; then 3 ranked
            hypotheses (claim / test / prediction), cheapest test first.

If you cannot trigger it on demand, finding a reliable repro is the task — say that instead of asking for a fix. [maxtdesign]

Explain template

Explain [thing] to a beginner with no [domain] background.
Constraints: [depth, length, no jargon or define it].
Give: a concrete example from THIS repo.
End with: the single sentence I should remember, and one thing
that would break if the key assumption were reversed.

Review template

Review [artifact] against [the locked decisions / the spec card].
Report only: correctness bugs · boundary violations · missing
failure handling. Cite the line and the rule broken for each.
Skip style nits. Give a confidence level per finding.
Confirm explicitly if you find nothing.

9 · Senior Questions Checklist

The questions a senior asks before starting. If you cannot answer them, you are not ready to spend the agent's cycle. [Serban]

  • ☐ What is the exit criterion? A specific, verifiable check — never "it works."
  • ☐ What breaks if this fails? Name the dependencies and their failure modes (FalkorDB down, stale read, bad data, rate limit).
  • ☐ Is it reversible? Reversible → move fast; irreversible → draw the system, decide deliberately.
  • ☐ Where are the boundaries? What is in scope, what is out, and which interfaces carry the uncertainty?
  • ☐ What is the context budget? Which files are ALWAYS, which ON DEMAND, which NEVER.
  • ☐ Which autonomy tier? Interactive, bounded sprint, or unattended batch — decided up front.
  • ☐ What is the bottleneck? The tightest resource sets the ceiling; you can move it, not remove it.
  • ☐ How will I verify? The exact command/assertion, run immediately after each action.
  • ☐ What feedback loops does this create? Will a retry, cache, or slowdown amplify or self-correct?
Six gates, a 5-line spec card, a 3-bucket context budget, a hypothesis-first debug loop, and a prompt library — the whole course on one printable page. If you can answer the §9 checklist, you can direct the agent instead of following it.
