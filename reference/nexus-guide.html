Do it

  1. Start FalkorDB (row 1 above). docker ps shows falkordb Up; open http://localhost:3000 for the Browser UI.
  2. Prove the connection: cd backend && uv run python health.py → FalkorDB OK — MATCH (n) RETURN count(n) => 1 (exit 0).
  3. Seed the cockpit graphs: uv run python scripts/seed_cockpit.py → prints both tenant lines, registry tenants=2, seed_cockpit OK. Re-run it — the counts are byte-identical (MERGE-based, idempotent).
  4. Start the backend, then: curl -s -w '\nHTTP %{http_code}\n' localhost:8000/api/tenants → the two-key JSON shown above, HTTP 200.
  5. Start the cockpit (npm run dev), then: curl -s -o /dev/null -w 'HTTP %{http_code}\n' http://localhost:5173/api/health → HTTP 200 (proves the Vite proxy path the browser uses).
  6. Optional whole-demo: docker compose up --build, then open http://localhost:5173.
Stop the database and re-run step 4. You should get HTTP 503, not stale data. If you still see tenants, something is falling back to a seed — that is the bug §4 is about.

3 · Walkthrough per track

Each track is proved by a script with a fixed expected stdout line. Run them in order; each is idempotent on re-run (every write is MERGE-based).

3.1 · Track 02 — the memory system, tier by tier

Key-focusCommand (cd backend)Expected stdout
H0 · named-graph routeruv run python scripts/verify_t0_engine.pyh0 ok — named_graph + ensure_indexes idempotent
Episodic memoryuv run python scripts/verify_t2_2.pyturns=2 order=user,agent
Semantic memoryuv run python scripts/verify_t2_3.pysemantic=1 facts=1 source=ok
Procedural memoryuv run python scripts/verify_t2_4.pyworkflow=1 steps=3 start=ingest
Handoff ledgeruv run python scripts/verify_t3_1.pyhandoffs=1 edge=1
Per-tenant isolationuv run python scripts/verify_t3_2.pytenant_a=3 tenant_b=0
High concurrencyuv run python scripts/verify_t3_3.pywriters=16 distinct=16 same=1

What each line means (the assertion behind it, read from the scripts):

  • turns=2 order=user,agent — two :Turn nodes written and recalled in timestamp order; the same user turn written twice stays one node (idempotent).
  • semantic=1 facts=1 source=ok — an :Entity and a :Fact linked by HAS_FACT, with a DERIVED_FROM edge back to the source :Turn (provenance).
  • workflow=1 steps=3 start=ingest — a stored :Workflow with a START step and a 2-edge NEXT_STEP chain, fetched and replayed with exactly one EXECUTED edge.
  • handoffs=1 edge=1 — a :Handoff ledger node plus one HANDED_TO skeleton edge; status defaults to PENDING; TARGETS points at the shared entity.
  • tenant_a=3 tenant_b=0 — tenant A's three turns are invisible to tenant B because the two graph keys differ, not because of a WHERE filter (D5).
  • writers=16 distinct=16 same=1 — 16 parallel writers lose nothing, and 16 writers on the same id collapse to one node (MERGE dedupes).

The write path that makes it real (from memory_service.py):

-- episodic: MERGE the Turn, then wire actor / session / topic / entities
MERGE (t:Turn {id: $id})
  ON CREATE SET t.timestamp = $timestamp, t.role = $role, t.text = $text
MERGE (actor)-[:PARTICIPATED]->(t)
MERGE (t)-[:IN_SESSION]->(session)
MERGE (t)-[:MENTIONS]->(entity0)

-- semantic: a fact hangs off its entity, and points back at the turn it came from
MERGE (e:Entity {id: $entityId})
MERGE (f:Fact {id: $id}) ON CREATE SET f.statement = $statement
SET f.confidence = $confidence
MERGE (e)-[:HAS_FACT]->(f)
MERGE (st:Turn {id: $sourceTurn})
MERGE (f)-[:DERIVED_FROM]->(st)

Sync the AST graph, then act on it. One command proves the whole track:

load#1 and load#2 being identical is the idempotency proof: graph_sync.py reads graphify-out/graph.json and MERGEs :File/:Symbol/:Test nodes and CALLS/IMPORTS/CONTAINS/INHERITS edges into code:graphhacks.

Blast radius — which symbols a change could break, bucketed by hop distance (falkor_action.py):

MATCH p=(root:Symbol {id:$symbolId})<-[:CALLS*1..2]-(affected:Symbol)
WHERE affected.id <> $symbolId
WITH affected, min(length(p)) AS hops
RETURN affected.id AS id, affected.label AS label,
       affected.source_file AS file, (affected:Test) AS is_test, hops
ORDER BY hops ASC, id ASC

Hotspots — the load-bearing symbols by PageRank over CALLS:

CALL algo.pageRank('Symbol','CALLS') YIELD node, score
RETURN node.id AS id, node.label AS label, node.source_file AS file,
       score ORDER BY score DESC LIMIT 5

Shortest dependency path — native algo.SPpaths, with a Cypher fallback:

MATCH (a:Symbol {id:$source}), (b:Symbol {id:$target})
CALL algo.SPpaths({sourceNode:a, targetNode:b, relTypes:['CALLS'],
    relDirection:'outgoing', maxLen:4, pathCount:1}) YIELD path
RETURN [n IN nodes(path) | n.id] AS node_ids,
       [r IN relationships(path) | type(r)] AS edge_types

Every action returns its own explanation. ActionEngine wraps each result in a DecisionTrace carrying the exact cypher, the params, the node_ids, the traversed edges, the hop_buckets, row_count, and elapsed_ms — all under graph == "code:graphhacks". That trace is the explainable answer (T4.3).

3.3 · Track 03 — the company brain

cd backend && uv run python scripts/verify_track3.py; echo exit=$?
track3 OK — repo=graphhacks people=1 commits=19 files=169 symbols=292 docs=49 owners=1 trace_docs=1 spec_drift=382 doc_drift=0 cited=100%
exit=0

Built on local data only (no GitHub token): git log --numstat + on-disk docs/·reference/·lessons/ + graphify-out/graph.json. The three resolvers:

who_owns — aggregate authorship over :MODIFIED, resolving a path or a symbol to files first (falkor_brain.py):

MATCH (p:Person)-[:AUTHORED]->(c:Commit)-[m:MODIFIED]->(f:File)
WHERE f.id IN $fileIds AND ($repo = '' OR f.repo = $repo)
RETURN p.id AS personId, p.name AS name, count(DISTINCT c) AS commits,
       sum(m.insertions) AS insertions, sum(m.deletions) AS deletions,
       max(m.at) AS lastTouched, collect(DISTINCT f.id) AS fileIds
ORDER BY commits DESC, lastTouched DESC
LIMIT 5

trace_why — cite every source that justifies a symbol or file. Evidence is the union of :DOCUMENTED_IN (name in a heading) and :MENTIONS (name in a body); OPTIONAL MATCH keeps a doc with no commit as a still-cited source:

MATCH (e:Symbol) WHERE e.id = $target OR e.name = $target
OPTIONAL MATCH (e)-[:DOCUMENTED_IN]->(hd:Doc)
OPTIONAL MATCH (e)<-[:MENTIONS]-(md:Doc)
WITH e, collect(DISTINCT hd.id) AS hIds, collect(DISTINCT md.id) AS mIds
RETURN e.id AS id, 'Symbol' AS kind, hIds + mIds AS docIds

detect_drift — spec drift (changed but undocumented) and doc drift (a doc still mentions a removed symbol). Removed symbols are flagged present=false, never deleted, so drift is observable:

MATCH (d:Doc)-[:MENTIONS]->(s:Symbol)
WHERE s.present = false AND ($repo = '' OR s.repo = $repo)
RETURN 'removed-symbol' AS kind, s.id AS id, s.name AS path_or_name,
       collect(DISTINCT d.path) AS docPaths

Run any single stage while debugging: uv run python scripts/verify_track3.py --step 3.5 → 3.5 ok — owners=1.

4 · The rule-3 flip — why FalkorDB is load-bearing

Rule 3 is the line that matters: if FalkorDB were removed, would the product still work? The cockpit used to answer “yes” because it rendered a hard-coded INITIAL_TENANTS seed. The data seam (src/data/remote.ts) now fetches /api/… with no fallback: a FalkorDB failure becomes a rejected promise and the app renders ErrorScreen. Here is the flip, reproduced live:

$ curl -s -o /dev/null -w 'nodes HTTP %{http_code}\n' \
    'http://localhost:8000/api/graph/nodes?tenant=graphsync_user1_ai_avatar_saas'
nodes HTTP 200

$ docker stop falkordb
falkordb

$ curl -s -w '\nHTTP %{http_code}\n' \
    'http://localhost:8000/api/graph/nodes?tenant=graphsync_user1_ai_avatar_saas'
{"detail":"FalkorDB unavailable (ConnectionError)"}
HTTP 503                      # → getJson throws → App loadState='error' → ErrorScreen

$ docker start falkordb
falkordb

$ curl -s -o /dev/null -w 'nodes HTTP %{http_code}\n' \
    'http://localhost:8000/api/graph/nodes?tenant=graphsync_user1_ai_avatar_saas'
nodes HTTP 200                # → Retry re-renders the graph

The same flip through the browser: reload http://localhost:5173 with FalkorDB stopped and the cockpit shows the error screen and its Retry button; restart FalkorDB, click Retry, and the seeded graph returns. That visible break is the submission — the product depends on the graph, so the graph is doing real work.

The simulation trap. Every feature had a fake version that worked with zero FalkorDB, so the demo “worked” while proving nothing. The flip is what converts a convincing mock into a graph-backed system. Record both HTTP codes (503 down / 200 up) as your evidence — you now have them.

No silent fallback, by design. src/data/index.ts no longer imports the seed; remote.ts deliberately has no fallback path. A read of an unknown tenant returns 200 with empty arrays and never creates a graph — the difference between “empty” (fine) and “down” (503) is exact, which is what makes the flip trustworthy.

You stop FalkorDB. Which outcome proves the graph is load-bearing, not decorative?

5 · The decisions — D5 / D6 / D8 / D9 / D10 in plain language

Each is an expensive-to-reverse choice recorded in docs/decisions.md. For rule 12 you need the one-sentence “why per decision”, cold. Every choice below is still a locked decision in AGENTS.md.

DecisionWhat it decidedWhy (the one-liner to say out loud)
D5 · one graph per tenantEpisodic + semantic + procedural memory live in one connected graph, one named graph per tenant (tenant:<id>).“Three separate stores look like three demos; one connected graph looks like a memory system — and per-tenant isolation is structural, not a WHERE filter.”
D6 · the MemoryService contractAll tiers go through one language-agnostic interface (docs/contracts/memory-service.md); every call takes tenant first; node/edge vocabulary fixed.“A single typed boundary lets each tier be built and verified independently and keeps the schema from drifting — and it kept a later language port possible.”
D8 · Python backendBackend and agent orchestration are Python/FastAPI with the official falkordb client; the frontend stays React/TS and talks HTTP/JSON. Supersedes D1 (Node).“I chose Python deliberately for clarity in the agent-memory code and accepted the rewrite cost — the contract was language-agnostic precisely so this was possible.”
D9 · modular cockpitThe ~1,985-line cockpit was decomposed under src/ with a single data-access seam (src/data/).“Isolating the data seam is what let the cockpit read the real API instead of a hard-coded seed — a pure refactor with no behavior change.”
D10 · named-graph projectionsAdds code:<repoId> (Track 01) and company:brain (Track 03) alongside tenant:<id>, all behind one router db.named_graph().“Tracks 01 and 03 reuse the same instance and router; tenant isolation is preserved and extended, not replaced.”
The rule-12 test for a decision is not “what is it” but “what did it buy, and what would it cost to undo?” D5 is expensive to reverse (schema). D9 was cheap (pure refactor). Say the reversibility out loud — that is what separates a decision from a preference.

Which decision records that code:<repoId> and company:brain join the tenant graphs on one FalkorDB instance?

6 · Vibe coder → principal architect — a ladder you can show in the graph

The cockpit's maturity dial exposes six levels. They are not decoration: the graph stores which agent produced each node at which level, so the progression is a query, not a claim.

LevelWhoWhat it sees
L0 · The Vibe CoderPlain-English features & safe re-promptsWhat the app does, live status, bubble-up safety alerts — no code.
L1 · Indie Hacker / PMUser flows, product rules & API economicsHidden AI assumptions and per-user token/unit costs.
L2 · Junior / Bootcamp DevSystem wiring & file guidesHow the frontend talks to the API routes and the database.
L3 · Full-Stack EngineerCode contracts, schemas & CypherReal TS interfaces, FastAPI endpoints, FalkorDB schemas.
L4 · Senior Staff EngineerConcurrency, security, GIL & blast radiusRace conditions, unthrottled spend, idempotency locks.
L5 · Principal / ResearcherBig-O, GraphBLAS & distributed theoryFormal complexity and citations.

Four agent personas own rungs of that ladder. They are :Agent nodes in the tenant graphs, linked to the nodes they produced by :PRODUCED, and linked to each other by a handoff ledger:

Agent (graph id)RungRole
VibeArchitect (agent:vibe-architect)L0–L1Turns a prompt into the vibe view and its unit economics.
FullStackBuilder (agent:fullstack-builder)L2–L3Wires UI → API → FalkorDB and writes the production code.
SeniorAuditor (agent:senior-auditor)L4–L5Audits security/spend and proves formal bounds.

The progression is persisted two ways. First, each concept node carries persona_level and created_by_agent, and the agent that made it is connected by PRODUCED. Second, the handoff ledger records state transfer across rungs with FROM_AGENT/TO_AGENT/TARGETS (and a direct HANDED_TO skeleton edge). Run this against a seeded tenant and the ladder prints itself:

Your arc is the project. Narrate it as: “I started at L0 — generated a foundation with AI and couldn't explain it. Then I moved up by doing L2/L3 work (contracts, a Python backend, a real data seam), L4 work (concurrency, load-bearing proofs, blast radius), and L5 work (systematic decisions, this guide). The graph records that arc — persona_level and the handoff ledger are the receipts.” That is the strongest possible answer to rule 12: not “I used AI”, but “I learned to direct it and to justify every choice.”

7 · Glossary + next

Use these terms exactly — they are the canonical language of this workspace (GLOSSARY.md).

TermMeaning here
Agent memoryPersistent, queryable state an agent reads and writes across sessions — not the context window, not RAG.
Episodic memoryTimestamped event nodes (:Turn) linked to the entities involved, so the agent recalls “what happened last time.”
Semantic memoryDurable factual knowledge — :Entity/:Fact and their relationships — independent of any one interaction.
Procedural memoryReusable workflow subgraphs (:Workflow/:Step) an agent can re-execute.
Three-tier memory modelThe composition of episodic, semantic, and procedural memory into one connected graph.
HandoffTransfer of state and responsibility between agents, recorded in the graph — not message passing.
Graph database / node / edgeData stored as nodes and typed, directed relationships traversed directly, rather than joined tables.
CypherThe declarative query language for FalkorDB, in which patterns are drawn with ASCII art.
Multi-graph / multi-tenant topologyFalkorDB holding many isolated graphs in one instance — one memory graph per tenant without a separate deployment.
MERGEThe clause that matches a pattern or creates it — the basis of idempotent memory writes.
GraphRAGRetrieval where the context is a subgraph traversed by relationships, not loose text chunks.
Spec card / exit criterionA five-line task brief, whose single verifiable check is stated before work begins.
