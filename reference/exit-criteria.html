Deriving Exit Criteria

The exit criterion is the highest-leverage line in a spec card. This is the recipe for producing one for any spec, every time.

← Curriculum Prompt playbook Lesson 0103

The one rule

An exit criterion is what an outside observer can check, pass/fail, without reading your code. If verifying it requires opening the source, it is an implementation detail, not an exit criterion.

The derivation recipe

  1. Restate the "what" as user-visible behaviour. "Wire FalkorDB" is activity; "the app shows memory stored in FalkorDB" is behaviour.
  2. Name the observer. You? A judge? A test script? The observer decides what counts as observable.
  3. Write it as Given / When / Then. Given <state>, when <one action>, then <one observable result>.
  4. Attach the command that produces the evidence. A check you cannot run is an opinion. State the exact command and the expected output.
  5. Add the load-bearing check and one failure case. For Track 02, every feature needs proof FalkorDB does real work (rule 3), plus what happens when the graph is missing.

The template

GIVEN  <starting state>
WHEN   <one action>
THEN   <one observable result>
PROOF  <the exact command and its expected output>
PLUS   <the FalkorDB-is-load-bearing check>

Anti-patterns

"Wire up FalkorDB"Activity, not a check"Loading the app shows a node that exists in FalkorDB"
"Uses MERGE"Implementation detail, not behaviour"Re-running the write twice leaves exactly one node"
"Memory works"UnverifiableRewrite as Given / When / Then
One criterion for the whole featureToo big to be one checkSplit the spec, or define the interface first (Lesson 0105)
If you cannot write a single Given / When / Then for a spec, the spec is either too vague or too big. That is a signal — not a failure. Split it, or define the contract first.
Take the next Track 02 feature you were about to build. Write its exit criterion with the template — one observable line + one command. If it takes more than one line, split the spec. Then hand the spec card to the agent and refuse to accept "done" without the proof output.
